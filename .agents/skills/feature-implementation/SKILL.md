機能追加・機能修正の依頼を受けた場合、このスキルの手順に従うこと。

本スキルが実行されたら、定義済みのサブエージェントを積極的に使うこと。
特に
* 設計： solution-architect
* コードレビュー: code-reviewer
* データベースレビュー : database-reviewer
* ドキュメント更新 : documentation-manager
* Railsコーディング : rails-implementer
* フロントエンドコーディング : frontend-implementer
* セキュリティレビュー : security-auditor
* テスト : test-engineer
* git, github 操作 : repository-operator
* 国際化・多言語化 : internationalization-implementer
* 翻訳完全性チェック : translation
* 画面案・スクリーンショットの参照解釈 : visual-reference-analyzer

の使用を推奨する。
他のエージェントについても必要に応じて起動して作業を進めてください。

国際化・多言語化が必要な時は internationalization スキルを使用すること。
ユーザー向け文言を変更した後は translation スキルで翻訳完全性を確認し、抜けがなくなるまで翻訳を補完すること。

## 並列実行ポリシー

独立して実行できるタスクは、サブエージェントや並列ツール呼び出しを使って**同時に実行する**こと。直列に並べるだけにしない。

- 静的解析（`bundle exec srb tc`、`bin/rubocop`、`bin/brakeman`、`bin/bundler-audit`、`bin/importmap audit`）や調査は相互に独立しているため、**同一メッセージで複数の bash ツール呼び出し**を行って並列実行する。
- 読み取り専用のサブエージェント（solution-architect、code-reviewer、database-reviewer、security-auditor、bug-investigator、test-engineer の調査など）は互いに依存がなければ、**同一メッセージで複数の task ツール呼び出し**を行って並列起動する。
- 編集を伴うエージェント（rails-implementer、frontend-implementer、translation、documentation-manager など）は、**変更ファイルが重複しない場合のみ並列**可。重複する場合は直列実行とする。並列起動時は各エージェントのスコープと変更対象ファイルをプロンプトで明示する。
- テストはテストDBやブラウザ資源を共有するため、全テストとシステムテストなどの重い実行は並列にせず直列化する。
- 編集系のタスクを先に完了させ、読み取り専用のレビュー・監査は編集完了後のスナップショットに対して実行する。編集とレビューを並列にする場合は、レビュー対象ファイルが編集対象と重複しないことを確認する。
- **大規模変更のレビュー**: 変更が複数レイヤーや多数のファイルに跨る場合は、役割・関心ごとにレビュー担当を分割して**同一メッセージで並列起動**する（例: 全体・統合観点は code-reviewer、DBは database-reviewer、セキュリティは security-auditor、UIは frontend-implementer 系）。ただし、ファイル間のインターフェイス不一致・重複コード・命名揺れ・横断的な問題（N+1等）を見る**統合観点のレビューを必ず1件残す**こと。指摘の重複・矛盾・誤検知はオーケストレータが突き合わせて解消する。変更が小規模な場合は分割せず1エージェントにまとめる。
- **ドキュメント同期の分担**: 対象文書が複数ある場合は文書単位で分担して並列起動する。**同一ファイルを複数エージェントに編集させない**（1文書内は1エージェント）。編集はコード変更が完了した最終スナップショットに対して行う。
- **システムテスト実行中の並列化**: システムテストは待ち時間が長いため、その実行中に読み取り専用のレビュー・監査（code-reviewer、security-auditor、database-reviewer 等）、機密情報スキャン、ドキュメント同期、翻訳の検出を**同一メッセージで並列起動**してよい（システムテストの bash は timeout を十分長く設定する）。ただし、実行中のサブエージェントにテスト・静的解析・ビルドを実行させない（CPU・テストDB競合によるフレーク防止）。翻訳の編集（locale ファイルの書き換え）はシステムテスト完了後に行うのを基本とし、並列で編集する場合は翻訳を検証するシステムテストを完了後に再実行する。
- **システムテスト失敗時の再検証**: システムテストが失敗して修正が入った場合、並列で得たレビュー・翻訳・ドキュメントの成果が陳腐化していないか確認し、**変更ファイルに関わる範囲だけ再検証**してから採用する（全体のやり直しはしない）。
- サブエージェントには、対象ファイル一覧・レビューまたは編集の範囲・観点をプロンプトで明示する。シェルを持たず `git diff` を実行できないエージェントがいるため、自分で差分を取得できる前提にしない。差分はオーケストレータが渡す。

**各フェーズにおいて、依頼内容・要件・設計の意図などで不明瞭な点があれば、その時点でユーザーに質問し、明確にしてから次に進むこと。** 推測で進めると手戻りが発生するため、不明点は必ず確認する。

## 役割分担

- **オーケストレータ（このスキルを実行するエージェント）**: フェーズ1〜7（要件整理・設計・チケット分割）、タスクエージェントへの委譲と検収、全体チェック、コミット・PR作成を担当する。
- **タスクエージェント（task ツールで起動）**: 割り当てられたチケット1件の実装を、小ループで完遂する。コミット・プッシュ・ブランチ操作は行わない。

## ブランチ運用フロー

1. **ブランチ作成**: フェーズ7（チケット分割）の完了・ユーザー承認後、実装開始直前に `main` ブランチからトピックブランチを作成する (`git checkout -b <ブランチ名>`)。
2. **実装〜全体チェック**: フェーズ8〜10を実行する。タスクエージェントはコミットしない。
3. **コミット**: 全チェック通過後、オーケストレータが機能の論理単位でまとめてコミットする。
4. **プッシュ**: `git push origin <ブランチ名>` でリモートにプッシュする。
5. **PR作成**: `gh pr create --base main --head <ブランチ名> --title "..." --body "..."` でプルリクエストを作成する。
6. **Codexレビュー〜マージ**: 下記「完了後のフロー」に従い、Codexレビューの確認・指摘対応・マージ・後片付けまで進める。

## 完了後のフロー（コミット・プッシュ〜Codexレビュー〜マージ・後片付け）

全チケットの実装と検証が終わったら、次の順で完了処理まで進める。詳細は `.agents/skills/codex-review/SKILL.md` に従う。

1. **コミット・プッシュ**: 変更を論理単位でコミットし（コミット前に `.agents/skills/security-check/SKILL.md` の機密情報スキャンを実行）、リモートへプッシュする。PRが未作成なら作成する。その後、Codexレビュー待機ループに入る。
2. **Codexレビューの定期確認**: `.agents/skills/codex-review/SKILL.md` の手順に従い、Codexのレビューを確認する。指摘は issue comments・インラインコメント・reviews の3箇所をすべて確認する。
3. **指摘対応**: 各指摘の妥当性を検証し、妥当なものは修正 → `fix:` コミット（日本語メッセージ）→ プッシュ → 再レビュー依頼を繰り返す。各修正ラウンドの検証は変更範囲の関連テストと静的解析のみとし、全テスト・全システムテストは修正がすべて完了した最終スナップショットで1回だけ実行する。妥当でない指摘は自己判断でスキップせず、理由を添えてユーザーへ報告し判断を仰ぐ。
4. **最終検証**: 妥当な指摘がなくなったら、マージ前にフェーズ9.4（`bin/rails test`）と、UI変更がある場合は9.5（`bin/rails test:system`）を最終スナップショットで実行し、通過を確認する。失敗した場合はフェーズ8〜9へ戻って修正する。
5. **マージ・後片付け**: 妥当な指摘が残っていないことを確認して main へマージする。その後 main へ切り替えて `git pull origin main`、作業ブランチをローカル・リモートともに削除する。

CI確認は `.agents/skills/ci-verification/SKILL.md` に従う。

## ワークフロー概要

フェーズ1〜7は**各フェーズの成果物がまとまった時点でユーザーに確認を求め、了承を得てから次のフェーズに進むこと**。フェーズ8〜10はユーザー確認なしで自律的に大ループを回してよい。

```
背景・目的の明確化
  ↓
理想と現実の検討 → 最終案の決定
  ↓
要件の洗い出し
  ↓
現状調査（コード・ライブラリ・既存UI/UX）
  ↓
設計方針 → インターフェイス設計 → 内部設計 → DB設計
  ↓
チケット分割・実行計画の作成
  ↓
ブランチ作成
  ↓
タスクエージェントへ委譲（依存関係に基づき並列/直列を制御）
  ↓  各エージェント内の小ループ:
  ↓  実装 → 静的解析 → 関連テスト → セルフレビュー → 動作確認 ↺
  ↓
完了報告の検収（全チケット）
  ↓
全体チェック:
  [並列] 型チェック / Rubocop / セキュリティスキャン
  → [直列] 全テスト → システムテスト
      └ 実行中に [並列] コードレビュー / セキュリティレビュー / 機密情報スキャン / ドキュメント同期 / 翻訳の検出
  → [並列] 翻訳の編集・補完（システムテスト完了後）
  ↓  問題があれば修正チケットを起票して委譲へ戻る（大ループ）
要件充足の確認
  ↓  未充足ならチケットを起票して委譲へ戻る（大ループ）
コミット → プッシュ → PR作成 → 報告
  ↓
Codexレビュー（定期確認・指摘対応） → マージ・後片付け
```

## フェーズ1: 背景・目的の明確化

依頼の背景と目的をユーザーに確認し、以下の項目を整理する。

- **背景**: なぜこの機能が必要か、何が課題か
- **目的**: この機能で何を達成したいか
- **スコープ**: やること・やらないことの境界
- **成功条件**: どうなったら完了と言えるかの明確な基準

成果物: 上記を箇条書きで一文ずつまとめたもの（ユーザーに確認すること）。不明点があれば確認してから次に進むこと。

---

## フェーズ2: 理想と現実の検討 → 最終案の決定

### 2.1 理想の洗い出し

実装制約を無視した理想の動作・UIを列挙する。

### 2.2 現実的な制約の確認

以下の観点から制約を洗い出す:

- **技術的制約**: 現在のスタック（Rails 8.1, Ruby 4.0.5, importmap + Stimulus, 開発・テストは SQLite・本番は PostgreSQL）で実現可能か
- **ライブラリ制約**: 追加ライブラリが必要か、既存ライブラリで代替可能か
- **期間制約**: おおまかな工数感
- **運用制約**: 既存機能との互換性、後方互換性、マイグレーションの要否

### 2.3 最終案の決定

理想と制約をすり合わせ、実装方針の最終案をユーザーに提案し、確認を得る。

成果物: 最終案の説明（箇条書きまたは短い文章、ユーザー確認済み）。案に確信が持てない場合は複数案を提示し、ユーザーに選んでもらうこと。

---

## フェーズ3: 要件の洗い出し

最終案を基に、実装レベルの要件を列挙する。

- 機能要件（何ができるべきか）
- UI要件（画面のどこに何が表示されるか、操作手順）
- 非機能要件（パフォーマンス、セキュリティ、アクセシビリティ）
- エラーハンドリング要件（異常系の振る舞い）
- テスト要件（どのようなテストケースが必要か）

各要件は `AGENTS.md` の記述ルールに従い日本語で記述すること。

要件は `docs/requirements.md` の該当セクションに追記すること（UI変更がある場合は特に）。画面デザインの参考として `docs/images/*.png` と `docs/mobile_images/` の対応する画面案を必ず参照すること。

成果物: 要件リスト（ユーザー確認済み） + `docs/requirements.md` への追記。要件の解釈に迷ったらユーザーに確認すること。

---

## フェーズ4: 現状調査

実装を始める前に、関連するコードの現状を把握する。

### 4.1 コード調査

- 追加・修正対象の機能に関連するファイルを特定する
- 類似機能の実装パターンを確認する（コントローラ、ビュー、モデル、ヘルパー、サービスのそれぞれ）
- 既存のテストを確認し、テストパターンを把握する

### 4.2 ライブラリ調査

- 今回の修正に使える既存ライブラリがあるか確認する
- 新規ライブラリ導入が必要な場合、Gemfile / importmap の管理ポリシーに合致するか確認する
- 代替案（既存ライブラリの機能で実現できないか）を検討する
- **外部ライブラリを追加する場合は、GitHub リポジトリで以下の観点を確認し、メンテナンスが継続されているものだけを選択すること:**
  - 最終コミットから1年以上経過していないか
  -  Issue や Pull Request が放置されていないか
  - 対応している Ruby / Rails のバージョンが現在のスタックと整合しているか
  - スター数やフォーク数である程度使われているか

### 4.3 UI/UX 一貫性調査

- 既存の同種画面・コンポーネントのデザインパターンを確認する
- 新しいコンポーネントを追加する場合、既存のコンポーネントの書き方・命名規則・レイアウトを確認する
- `docs/requirements.md` のデザイン要件セクションおよび `docs/images/*.png` と `docs/mobile_images/` のスクリーンショットを参照する（必要に応じて visual-reference-analyzer で画像内容を解釈する）
- テーマ（light/dark）対応が必要な場合、既存のCSS変数とクラス分岐パターンを確認する

成果物: 調査結果の整理（ファイルパス・使用ライブラリ・既存パターンの引用を明記）

## フェーズ5: 設計方針

調査結果を基に設計方針を定める。

- **アーキテクチャ上の配置**: どのレイヤーに何を追加するか（コントローラ、モデル、ビュー、ヘルパー、サービス、JavaScript、CSS）
- **既存パターンとの整合**: 類似機能と同じパターンに従うか、新しいパターンを導入するか
- **命名規則**: クラス名、メソッド名、ファイル名、ルートパラメータ、DBカラム名の命名方針
- **エラー設計**: エラーの種類とハンドリング方法

成果物: 設計方針のドキュメント（ユーザーに確認すること）。トレードオフがある場合は理由を含めて提示し、判断を仰ぐこと。

## フェーズ6: 詳細設計

### 6.1 インターフェイス設計

- コントローラのアクションとルーティング
- ビューで渡すインスタンス変数
- ヘルパーメソッドのシグネチャ
- サービスオブジェクトのパブリックメソッド
- JavaScript のイベントとStimulusコントローラのAPI

### 6.2 内部設計

- 非同期処理の有無と方法

### 6.3 DB設計

- 新しいテーブル・カラムの追加仕様
- インデックス
- マイグレーションの前後でのデータ整合性
- SQLite / PostgreSQL 両アダプタで動作することの確認

成果物: 設計ドキュメント（ユーザーに確認すること）。判断に迷う選択肢があれば、理由付きで提示して選んでもらうこと。

## フェーズ7: チケット分割・実行計画

詳細設計をもとに、実装作業をタスクエージェントへ委譲可能な単位のチケットに分割する。

### 7.1 チケットの作成

各チケットには以下を含めること:

- **タイトル**: 内容が一目で分かる名前
- **目的**: 何を実現するか
- **スコープ**: 対象ファイル・レイヤー、やること・やらないこと
- **依存チケット**: 先行完了が必要なチケット（あれば）
- **完了条件**: 追加・更新するテスト、期待される振る舞い、通過すべきチェック

粒度の目安:

- 1チケット = 1エージェントが1コンテキストで完結できる大きさ
- チケット数は2〜10程度を目安とし、大きすぎるチケットはさらに分割する
- 1行修正レベルの細かすぎる分割は避ける

### 7.2 依存関係の分析と実行計画

- チケット間の依存関係（DBスキーマ → モデル → コントローラ/ビュー、共通ヘルパー → 利用側など）を洗い出す
- 依存のないチケットは並列グループ、依存のあるチケットは直列の順序付けを行い、実行計画を作成する
- **並列グループ内のチケットは変更ファイルが重複しないようにすること**。重複が避けられない場合は同一チケットに統合するか直列実行とする
  - 注意: 本リポジトリは `test/integration/blog_flow_test.rb` にアサーションが集中するため、複数チケットがこのファイルに追記する場合は特に競合しやすい
  - ビュー（ERB）とStimulusのようにDOM契約（`data-*` 属性、クラス名、送信フォームの構造・順序）を共有するチケットは、設計段階で契約を凍結してプロンプトへ明記する。凍結が難しい場合は1チケットへ統合するか直列実行とする（契約のずれはシステムテストで初めて破綻が分かるため）

成果物: チケット一覧 + 実行計画（並列/直列のグループ分け）。会話内で提示し、ユーザーの承認を得ること。ファイルには保存しない。

## フェーズ8: ブランチ作成・タスクエージェント実行

### 8.1 ブランチ作成

`main` の最新から作成する:

```bash
git checkout main && git pull origin main
git checkout -b <ブランチ名>
```

### 8.2 タスクエージェントへの委譲

- 実行計画に従い、task ツールでタスクエージェントを起動する。並列グループは同一メッセージで同時に起動し、直列チケットは先行チケットの検収完了を待ってから起動する
- 各エージェントへのプロンプトには最低限以下を含めること:
  - チケットの内容（目的・スコープ・完了条件）
  - 設計方針・詳細設計のうち該当部分
  - 関連ファイルのパスと既存パターンの説明（フェーズ4の調査結果）
  - 制約:
    - コミット・プッシュ・ブランチ操作を行わないこと
    - チケットのスコープ外のファイルを変更しないこと（必要になった場合は報告して指示を仰ぐこと）
    - コードコメントはユーザーから要求された場合のみ追加すること
    - コミュニケーション・完了報告は日本語で行うこと
    - 実行してよいのは関連テストと変更ファイルの静的解析のみとし、**全体テスト・全システムテストは実行しないこと**（例外は親が明示的に指示した場合のみ）
  - 8.3 の小ループ手順
  - 8.4 の完了報告フォーマット

### 8.3 小ループ（各タスクエージェントが遵守する手順）

1. **実装**: チケットのスコープ内でコードを書く
2. **静的解析**: 変更ファイルに対して `bin/rubocop <変更ファイル>` を実行。RubyまたはRBIを変更した場合は `bundle exec srb tc` も実行
3. **関連テスト**: チケットで追加・変更した機能に関係するテストだけを実行する（例: `bin/rails test test/integration/blog_flow_test.rb -n test_xxx`）。**全体テスト・全システムテストは実行しない**。タスクエージェントが実行してよいのは関連テストと変更ファイルの静的解析のみであり、全体検証は親（オーケストレータ）の責務とする（例外: 親が明示的に指示した場合のみ）
4. **セルフコードレビュー**: フェーズ9.7と同じ観点で自分の差分をレビューする
5. **動作確認**: 完了条件を満たすことを確認する（テスト結果に加え、必要に応じて `rails console` 等での検証）
6. 問題があれば 1 に戻る。完了条件をすべて満たしたら完了報告をして終了する

### 8.4 完了報告フォーマット

- 実施した内容の概要
- 追加・変更したファイルのリスト
- 実行したチェックとテストの結果
- 残課題・懸念事項（あれば）

### 8.5 検収（オーケストレータ）

- 報告内容がチケットの完了条件をすべて満たすか確認する。必要に応じて差分や関連テストの実行結果を自分でも確認する
- 不十分な場合は不足点を明示して修正を依頼する（同じエージェントへの追加指示、または新規エージェントの起動）
- 全チケットを検収したらフェーズ9へ進む

## フェーズ9: 全体チェック（大ループ）

全チケット検収後、オーケストレータが変更全体に対して以下を実行する。

**実行方針（重複実行の回避）**: 同一の変更スナップショットに対して、各静的解析・全体テスト・システムテストはそれぞれ1回だけ実行する。完了報告済みの同一結果を理由なく再実行しない。コード・テスト・設定が変わった場合のみ該当検証を再実行する。ただし**修正ラウンド（レビュー指摘対応・`fix:` コミット）中は、変更範囲に関わる関連テストと静的解析のみを再実行し、全テスト・システムテストは最終スナップショットで1回だけ実行する**。失敗時は原因を分類（コード起因／テスト起因／環境起因）して記録し、同じコマンドを無意味に繰り返さない。

**並列実行**: 独立した検証は同一メッセージから同時に実行し、直列に並べるだけにしない。

- 9.1〜9.3（Sorbet・Rubocop・セキュリティスキャン）は相互に独立しているため、複数の bash ツール呼び出しを同一メッセージで行って並列実行する。
- 9.4 と 9.5 はテストDB・ブラウザ資源を共有するため並列にせず、9.4 → 9.5 の直列で実行する。
- 9.6 の翻訳補完と 9.9 のドキュメント同期は編集を伴うため、変更ファイルが重複しないことを確認してから同一メッセージで並列起動する（重複する場合は直列）。
- 9.5 の実行中に、9.7 のレビュー系（code-reviewer、security-auditor）、9.8 の機密情報スキャン（security-check）、9.9 のドキュメント同期、9.6 の翻訳の検出を**同一メッセージで並列起動**してよい（実行中のサブエージェントにテスト・静的解析・ビルドを実行させない）。翻訳の編集（locale ファイルの書き換え）は 9.5 完了後に実行する。
- システムテストが失敗して修正が入った場合は、並列で得たレビュー・翻訳・ドキュメントの成果を変更ファイルに関わる範囲だけ再検証してから採用する。

### 9.1 型チェック（Sorbet）

Ruby・RBI・依存関係の変更を含む全体に対して実行する。Gem依存を変更した場合は先に `bin/tapioca gem`、Rails DSL に由来する型情報を変更した場合は先に `bin/tapioca dsl` を実行し、生成RBIを同期する。

```bash
bundle exec srb tc
```

### 9.2 構文・スタイルチェック（Rubocop）

```bash
bin/rubocop
```

### 9.3 セキュリティスキャン

```bash
bin/brakeman --no-pager
bin/bundler-audit
bin/importmap audit
```

`bin/importmap audit` は importmap・JavaScript 依存を変更した場合に実行する。

### 9.4 全テスト

同一の変更スナップショットに対して1回だけ実行する:

```bash
bin/rails test
```

### 9.5 システムテスト

UI・画面挙動の変更がある場合のみ実行する。全体テストと同じく同一スナップショットで1回だけ実行する:

```bash
bin/rails test:system
```

待ち時間が長いため、実行中は 9.6 の翻訳の検出、9.7 のレビュー、9.8 の機密情報スキャン、9.9 のドキュメント同期を同一メッセージで並列起動してよい。フェーズ冒頭の「並列実行」に示す条件（サブエージェントにテスト・静的解析・ビルドを実行させない、失敗時は変更範囲だけ再検証）に従うこと。

### 9.6 翻訳完全性チェック

ユーザー向け文言、locale ファイル、ビュー、flash、バリデーション、メール、ジョブ、通知、JavaScript を変更した場合は、translation スキルの手順に従い、translation エージェントを起動して翻訳完全性を確認する。

1. 全対象localeファイル間で翻訳キーの欠落をチェックする。
2. 直書きのユーザー向け文言が残っていないか検索する。
3. 未翻訳キー・直書き文言があれば translation エージェントに翻訳補完を委譲する。
4. 補完後、再度 1〜2 を実行し、未翻訳がなくなるまで繰り返す。
5. 翻訳の変更によって既存テストが壊れていないか、関連テストを実行する。

9.9 のドキュメント同期と変更ファイルが重複しない場合は、translation エージェントと documentation-manager を同一メッセージで並列起動してよい。

### 9.7 コードレビュー（変更全体）

code-reviewer を起動し、チケット単位ではなく変更全体を通して、以下の観点で見直す。security-auditor と 9.8 の機密情報スキャン（security-check）は独立しているため、code-reviewer と同一メッセージで並列起動してよい。変更が複数レイヤーに跨る場合は database-reviewer などの担当も加えて役割分担するが、統合観点のレビューは必ず1件残すこと。確認すべき点が不明な場合はユーザーに判断を仰ぐこと:

- **要件充足**: 全ての要件を満たしているか
- **エッジケース**: 空データ、異常値、認証なし、権限不足のケースを網羅しているか
- **エラーハンドリング**: ユーザーに適切なエラーメッセージが表示されるか
- **N+1**: データベースクエリにN+1が発生していないか
- **セキュリティ**: SQLインジェクション、XSS、CSRFの対策ができているか
- **チケット間の統合**: 重複コード、命名揺れ、インターフェイスの不一致、チケット間で矛盾した実装がないか
- **既存コードとの一貫性**: 同じ問題に対して同じパターンで解決しているか
- **CSSクラス名**: 既存の命名規則に従っているか
- **JavaScript**: Stimulus コントローラの規則に従っているか

### 9.8 機密情報スキャン

`.agents/skills/security-check/SKILL.md` の手順に従い、コミット対象の変更ファイルを対象とした機密情報スキャンを実行する。リポジトリ全体のスキャンはユーザーが明示的に指定した場合のみ実行する。

- 🔴 CRITICAL または 🟠 HIGH の指摘が見つかった場合は作業を中断し、ユーザーに報告して指示を仰ぐこと
- 🟡 MEDIUM 以下の指摘のみの場合は報告を行うが、ユーザーの判断で継続してよい

### 9.9 ドキュメント同期

実装・設定・テスト・運用の変更により `docs/` 以下の仕様書・README・デプロイ・運用文書と差異が生じる場合は、差分と根拠を添えて documentation-manager を起動し、ドキュメントを同期する。監査のみを依頼する場合は先に差分と根拠の報告を受けたうえで、更新の明示委譲を行ってから編集させる。対象文書が複数ある場合は文書単位で分担して並列起動してよい（同一ファイルを複数エージェントに編集させない）。

9.6 の翻訳補完と変更ファイルが重複しない場合は並列起動してよい（重複する場合は直列）。同期結果はフェーズ10の要件充足確認とあわせて確認する。

**レビュー・修正後の再確認**: 9.7のレビューやレビュー指摘の修正（`fix:` コミット）で実装・設定が変わると、先に同期したドキュメントが陳腐化する。指摘修正が入った場合は、最終スナップショットでドキュメントの該当記述（値・属性名・仕様）を再確認し、差分があれば documentation-manager で再同期してからフェーズ10へ進む。

### 9.10 問題発見時の対応

いずれかのチェックで問題が見つかった場合、修正内容をチケット化（完了条件を明記）し、フェーズ8へ戻って大ループを回す。修正チケットの規模が小さく依存もなければ、直列1件のチケットとして1エージェントに委譲する。

修正ラウンド後の再検証は、変更ファイルとその波及先に限った関連テスト・型チェック・Rubocop に限定する。全テスト・全システムテストは、修正がすべて完了した最終スナップショットで1回だけ実行する。

## フェーズ10: 要件充足の確認

フェーズ3の要件リストと突き合わせ、未充足の要件がないか確認する。

- 未充足の要件がある場合はチケットを起票し、フェーズ8へ戻って大ループを回す
- 全要件を充足し、フェーズ9の全チェックを通過したらフェーズ11へ進む

## フェーズ11: コミット・報告・PR作成・CI確認

1. `git status` / `git diff` で変更内容を最終確認し、意図しない変更が混入していないか確認する
2. 機能の論理単位でコミットを分割してコミットする（日本語メッセージ）

```bash
git add <該当ファイル>
git commit -m "{日本語のコミットメッセージ}"
git push origin <ブランチ名>
```

3. PR を作成する

```bash
gh pr create --base main --head <ブランチ名> --title "..." --body "..."
```

4. **CI確認**: CI は `main` への push 時のみ実行されるため、PRブランチでは確認できない。PR作成後は「完了後のフロー」の Codex レビューへ進み、main へのマージ後に `.agents/skills/ci-verification/SKILL.md` の手順に従い CI を確認する。CIが失敗した場合は同スキルに従い修正ループを回す。

5. 以下の内容をユーザーに日本語で報告する:

- 実施した内容の概要
- 消化したチケットの一覧
- 追加したファイルのリスト
- 変更したファイルのリスト
- （必要な場合）動作確認方法や注意点
- CIの確認結果（PRブランチではCIは実行されないため、mainマージ後に確認する旨）
- 残課題（未対応・既知の問題・フォローアップが必要な点があれば）
- PR のURL（レビューを依頼する）

6. 「完了後のフロー」に従い、Codexレビューの定期確認・妥当な指摘への対応・指摘がなくなった後のmainへのマージ・後片付けまで進める。
