GitHubのIssueを確認して対応するよう指示された場合、このスキルの手順に従うこと。

本スキルはオーケストレータであり、個々のIssueの実装・検証・マージは既存スキルに委譲する。

- **不具合・エラー・期待動作との差異** → `.agents/skills/bug-fix/SKILL.md`（skill ツールで `bug-fix` をロード）
- **機能追加・仕様変更・改善** → `.agents/skills/feature-implementation/SKILL.md`（skill ツールで `feature-implementation` をロード）
- **コミット前の機密情報チェック** → `.agents/skills/security-check/SKILL.md`
- **プッシュ後のCI確認** → `.agents/skills/ci-verification/SKILL.md`
- **PR作成後のCodexレビュー・マージ** → `.agents/skills/codex-review/SKILL.md`
- **ドキュメントのみのIssue** → `.agents/skills/documentation-authoring/SKILL.md`

対象スキルのフェーズゲート（ユーザー確認）・検証・完了フローは省略しないこと。本スキルはその前段（Issueの収集・分類・順序決定）と、グループ間の進行管理を担う。

**各フェーズにおいて、Issueの内容・期待動作・優先度が不明瞭な場合は、その時点でユーザーに確認し、明確にしてから次に進むこと。** 推測で進めると手戻りが発生するため、不明点は必ず確認する。ユーザーがIssueの起票者である場合は、Issueへのコメント追加を提案してもよい。

## 基本方針

- **順次対応**: 1グループの対応（PRマージとIssueクローズ確認）が完了してから次のグループに着手する。別グループを並列で進めない（ブランチ・レビュー・検証の混在を避ける）。
- **勝手に束ねない**: 「一度の変更で対応するもの」は同一の画面・機能・根本原因など、1つのまとまった変更としてレビュー・検証できる場合に限る。無関係なIssueを工数削減のために同梱しない。
- **Issueに書かれた内容が受入基準**: Issueの期待動作を満たしたときに完了とする。Issueに書かれていない改善をスコープに含めない。
- **スコープを広げない**: 対応中に別の不具合や改善点を見つけても、勝手に直さず、新規Issueとして起票することをユーザーに提案する。
- **Issueを勝手に閉じない**: PRマージによる自動クローズを使い、自動で閉じなかった場合のみ手動クローズする（フェーズ4.4）。

## サブエージェントの利用

個別Issueの実装フェーズでは、対象スキル（bug-fix / feature-implementation）の指示に従い、solution_architect、bug_investigator、rails_implementer、frontend_implementer、test_engineer、database_reviewer、code_reviewer、security_auditor、documentation_manager、repository_operator、release_operator などのサブエージェントを積極的に使うこと。

分類・グルーピングの判断に迷う場合は、solution_architect（機能・改修）または bug_investigator（不具合）に読み取り専用の調査を依頼し、対象ファイル・根本原因の重複を確認してからグルーピングしてもよい。

## ワークフロー概要

```
フェーズ0: 前提確認（gh認証・作業ツリー・main最新化）
  ↓
フェーズ1: オープンIssueの収集
  ↓
フェーズ2: Issueの精査・分類（種別判定 → グルーピング → 対応順序）
  ↓
フェーズ3: 対応計画の提示・ユーザー承認
  ↓
フェーズ4: グループごとに対応（以下をグループ数だけ繰り返す）
  main最新化 → 対象スキルをロードして実行
    → PR本文に Fixes #N を記載 → Codexレビュー → マージ
    → Issueクローズ確認 → 中間報告
  ↓
フェーズ5: 全グループ完了まで順次ループ
  ↓
フェーズ6: 完了報告
```

## フェーズ0: 前提確認

以下を確認する。問題があればユーザーに知らせて対応を仰ぐ。

```bash
env -u GH_TOKEN gh auth status
git status --short
git branch --show-current
git checkout main && git pull origin main
```

- 作業ツリーに未コミットの変更が残っていないこと（残っている場合はユーザーに確認する）
- `gh` が認証済みであること。401 `Bad credentials` が出る場合は `env -u GH_TOKEN` を付けて実行する（無効な `GH_TOKEN` がホスト側認証を上書きするため）
- main が最新であること

## フェーズ1: オープンIssueの収集

オープンなIssueを古い順に取得する。

```bash
env -u GH_TOKEN gh issue list --state open --limit 100 \
  --json number,title,labels,assignees,milestone,createdAt,updatedAt,body \
  --jq 'sort_by(.number)'
```

各Issueについて、コメントを含めて詳細を確認する（起票後の補足・仕様変更・追加情報がコメントに書かれている場合がある）。

```bash
env -u GH_TOKEN gh issue view <番号> --comments
```

### 除外・保留の判定

- `wontfix` / `duplicate` / `invalid` ラベルが付いたIssueは対象外とする
- オープンなPRに紐付いているIssue（対応中・レビュー中）は一覧ではスキップする。紐付けはタイムラインの cross-reference で確認する:

```bash
env -u GH_TOKEN gh api repos/{owner}/{repo}/issues/<番号>/timeline --paginate \
  --jq '[.[] | select(.event == "cross-referenced") | select(.source.issue.pull_request != null) | {number: .source.issue.number, state: .source.issue.state}]'
```

オープンPRが1件でもあれば「対応中」としてスキップし、その旨を計画に記録する。マージ済みPRのみの場合は未対応として扱う。

- `question` ラベルのIssueは対応要否をユーザーに確認する
- 対象件数が多い場合は、直近のIssueから処理するか全件処理するかをユーザーに確認する

成果物: 対象Issueの一覧（番号・タイトル・起票日・コメント要約・スキップ理由）

## フェーズ2: Issueの精査・分類

各Issueについて、種別・グルーピング・順序を判断する。

### 2.1 種別判定（使用スキルの決定）

| 種別 | 判断基準 | 使用スキル |
|---|---|---|
| 不具合 | 期待動作と実際の動作の差異、エラー、データ不整合、表示崩れ | `bug-fix` |
| 機能追加・仕様変更 | 新しい機能、既存機能の拡張・変更、UI/UX改善 | `feature-implementation` |
| ドキュメントのみ | 仕様書・README等の記載のみの変更（コード変更なし） | `documentation-authoring`（ユーザー確認のうえ） |
| その他 | 質問、運用相談、方針検討など | 対応せず回答内容をユーザーに相談 |

### 2.2 グルーピング

「一度の変更で対応するもの（同一変更グループ）」と「個別に対応するもの」に分ける。

**同一変更グループにしてよい条件（すべて満たす場合）:**

- 同一の画面・機能・帳票など、変更対象ファイルが重複または近接している
- 同じ根本原因、または同じ設計方針の変更であり、1つの変更として自然にまとまる
- 1ブランチ・1PRとしてレビュー・検証できる大きさである（目安: 3〜5 Issue以内）
- システムテストの対象領域が共通で、まとめて回帰確認できる

**個別対応にする条件（いずれかに該当）:**

- 独立した機能・画面で、別々に検証・リリースしたい
- DBマイグレーションや大規模な設計変更を伴う
- 他のIssueと変更内容が矛盾する、または先のIssueの判断結果に依存する
- 1 Issue単体でPRを分けた方がレビューしやすい・安全である
- 機能追加で、feature-implementation のチケット分割が必要な規模である（原則1 Issue=1グループ）

判断に迷う場合は、対象ファイルの重複を調査してから決める。同一ファイルを触るだけで関連性が薄い変更は、コンフリクト回避のため個別対応とする。

### 2.3 対応順序の決定

グループの対応順序は以下を優先して決める:

1. ユーザーが指定した優先度
2. 実運用への影響が大きい不具合（本番停止・主要機能不可 > 表示のみ）
3. 依存関係の上流にあるグループ
4. 起票が古いIssue

成果物: Issueごとの種別・グループ分け・対応順序（ユーザー確認前の案）

## フェーズ3: 対応計画の提示・承認

フェーズ2の分類結果を以下の形式でユーザーに提示し、承認を得る。

```
## Issue対応計画（全N件）

### グループ1: <テーマ>（一度の変更で対応 / 使用スキル: <bug-fix|feature-implementation>）
- #<番号> <タイトル>
- #<番号> <タイトル>
- 理由: <同一画面・同一根本原因 など>

### グループ2: <テーマ>（個別対応 / 使用スキル: <...>）
- #<番号> <タイトル>

### スキップ・保留
- #<番号> <タイトル>: <理由（対応中PRあり / question など）>

### 対応順序
グループ1 → グループ2 → ...（理由）
```

- グループ分け・順序への修正要望があれば反映してから着手する
- ユーザーの了承を得てからフェーズ4に進む

## フェーズ4: グループごとの対応（グループ数だけ繰り返す）

### 4.1 mainの最新化

グループ対応の開始前に必ず実行する（前のグループのマージを反映する）。

```bash
git checkout main && git pull origin main
git status --short
```

### 4.2 対象スキルのロードと実行

グループの種別に応じて skill ツールで対象スキルをロードし、その手順に従ってグループ内の全Issueをまとめて対応する。

- **bug-fix**: グループ内のIssueを「不具合報告」として扱い、フェーズ1で内容を整理する。複数Issueは1つの修正として扱う
- **feature-implementation**: グループ内のIssueを要件としてフェーズ1〜3で整理する。チケット分割・実行計画はオーケストレータがグループ全体で一括して行い、1ブランチ・1PRにまとめる

対象スキルの手順に従い、ブランチ作成 → 実装 → 検証 → レビュー → セキュリティチェック → コミット → プッシュ → PR作成まで進める。スキル間の横断的な注意点:

- グループ内の複数Issueのうち一部だけが大きい場合は、feature-implementation のチケット分割の中でIssue単位のチケットとして扱い、PRはグループで1つにまとめる
- Issueの内容と実装が食い違う判断が必要になった場合は、勝手に決めずユーザーへ確認する
- グループの途中で対象外の修正が必要になった場合はスコープを広げず、新規Issueの起票を提案する

### 4.3 PRとIssueの紐付け

PR本文に、対象Issueをクローズするキーワードを必ず記載する（複数可）。

```
Fixes #167
Fixes #168
```

- マージ先はデフォルトブランチ（main）であり、マージ時に自動クローズされる
- コミットメッセージにも `refs #<番号>` を付けると追跡しやすい（必須ではない）
- PRタイトル・本文は既存の慣行（日本語）に合わせる

### 4.4 Codexレビュー・マージ・Issueクローズ確認

1. `.agents/skills/codex-review/SKILL.md` に従い、Codexレビュー・指摘対応・mainへのマージ・後片付けを行う
2. マージ後、対象Issueがクローズされたか確認する:

```bash
env -u GH_TOKEN gh issue view <番号> --json state --jq '.state'
```

3. `CLOSED` になっていない場合は、手動でクローズする:

```bash
env -u GH_TOKEN gh issue close <番号> --comment "PR #<PR番号> のマージにより対応しました。"
```

4. マージ後のmainをローカルへ取り込む:

```bash
git checkout main && git pull origin main
```

5. グループの結果を中間報告する（Issue番号・PR URL・クローズ状態・次に進むグループ）

---

## フェーズ5: 順次ループ

未処理のグループが残っている場合、フェーズ4に戻って次のグループを処理する。

- 前のグループのマージとIssueクローズが確認できるまで次のグループを開始しない
- グループ対応中に新たなIssueが起票された場合は、計画を見直すかユーザーに確認する
- 同じグループが再度失敗した場合は、原因（コード起因 / テスト起因 / 環境起因）を分類してユーザーに報告する

---

## フェーズ6: 完了報告

全グループの処理が完了したら、以下の形式で報告する。**報告は日本語で行う**（中国語など他言語を混入させない）。

```
## Issue対応完了レポート

### 対応結果
| Issue | タイトル | 種別 | 対応 | PR |
|-------|---------|------|------|----|
| #167 | ... | 不具合 | ✅ クローズ | #172 |
| #168 | ... | 仕様変更 | ✅ クローズ | #173 |

### スキップ・保留
- #<番号> <タイトル>: <理由>

### 残課題・注意点
- 実装中に発見した別の問題（新規Issue化の提案）
- デプロイ時の注意点
```

## 注意事項

- **順次実行を厳守**: グループを並列で進めない。1グループのマージが完了してから次に着手する
- **対象スキルの完了フローを省略しない**: コミット前の機密情報スキャン、プッシュ後のCI確認、Codexレビュー、マージ、後片付けは対象スキルの指示どおり実行する
- **Issueの自動クローズを基本**: PR本文の `Fixes #N` を使い、手動クローズは自動で閉じなかった場合のフォールバックとする
- **Issueの内容を勝手に解釈しない**: 曖昧な点はIssueへのコメント追加またはユーザーへの質問で明確にしてから進める
- **無関係なIssueを束ねない**: グルーピングは変更対象・根本原因の重複を根拠とする
- **ユーザーの明示指示なくIssueをクローズしない**: 自動クローズ（PRマージ）と、クローズ確認後のフォールバック手動クローズのみ
- `git reset --hard`、`git clean`、force push、履歴書き換えは実行しない
- Issue対応の途中経過は、グループ完了ごと・問題発生時に報告する（対応中に細かな進捗報告は不要）
