# ドキュメント作成

根拠を追跡でき、読み手が判断・実装・検証に使える文書を作成する。現行仕様、将来要件、提案、未確定事項を混同しない。

本スキルが実行されたら、定義済みのサブエージェントを積極的に使うこと。
特に
* 設計： solution_architect
* コードレビュー: code_reviewer
* データベースレビュー : database_reviewer
* ドキュメント更新 : documentation_manager
* Railsコーディング : rails_implementer
* フロントエンドコーディング : frontend_implementer
* セキュリティレビュー : security_auditor
* テスト : test_engineer
* git, github 操作 : repository_operator
* リリース・運用操作 : release_operator

の使用を推奨する。
他のエージェントについても必要に応じて起動して作業を進めてください。
各サブエージェントが使用するLLMモデルについては、`.codex/agents/` の各定義で指定されているモデルを使用すること。

## 基本原則

- リポジトリの `AGENTS.md` と、対象ディレクトリに適用される追加指示を最初に確認する。
- ユーザーの明示指示を最優先し、指定されたテンプレート、章立て、用語、保存先、文体を維持する。
- 事実を創作しない。根拠が不足する内容は推測で確定せず、`未確定`、`要確認`、または `提案` と明記する。
- コードが示す「現行動作」と、資料や依頼が示す「期待仕様」を区別する。不一致を黙って一方へ合わせない。
- 要件には識別子と検証可能な受入条件を付け、設計・実装・テストとの追跡可能性を確保する。
- 既存文書の更新では、関係のない節の言い換え、並べ替え、整形を避け、必要最小限の差分にする。
- 文書だけを変更する。コード、設定、DB、外部サービスは、ユーザーが別途依頼しない限り変更しない。
- 監査またはレビューだけを依頼された場合は編集せず、差分候補と根拠を報告して明示的な更新依頼を待つ。

## ワークフロー

### 1. 依頼を分類する

次を特定する。

- 作業種別: 新規作成、既存文書の更新、実装同期、レビュー、統合
- 文書種別と主な読者
- 文書で支援する判断または作業
- 対象範囲と対象外
- 保存先、形式、テンプレート、完了条件

文書種別と章立てを選ぶ場合は [document-templates.md](references/document-templates.md) を読む。複数種別が必要でも、同じ内容を重複記載せず、正本と参照関係を決める。

合理的な仮定で戻せる範囲は進め、構成や結論を大きく変える不明点だけをユーザーに確認する。

### 2. 根拠を収集する

次の優先順を目安に、依頼に必要な範囲だけ読む。

1. ユーザーの明示指示と提供資料
2. 適用される `AGENTS.md` と指定テンプレート
3. 正本として指定された要件書・仕様書・設計書
4. `docs/requirements.md`、`docs/deployment.md`、`docs/backup-requirements.md`、`docs/manuals/`、関連する `docs/images/`・`docs/mobile_images/`
5. 対象機能のコード、DBスキーマ、設定、テスト
6. README、運用文書、変更差分、必要に応じた履歴

対象ファイルを `rg --files` と `rg` で絞り込む。巨大ファイルや埋め込み画像データは、必要な見出しや語句だけを検索して読む。

外部仕様、法令、ライブラリ仕様、変動し得る情報を記載する場合は、必要に応じて一次情報を確認し、参照元と確認日を残す。

### 3. 事実と不確実性を整理する

執筆前に、少なくとも次へ分類する。

- **確定**: ユーザー指示または信頼できる根拠で確認できる内容
- **現行**: 現在のコード、設定、運用が示す内容
- **推論**: 複数の根拠から導いたが明記されていない内容
- **提案**: 今後採用する候補
- **未確定**: 判断材料が不足し、確認が必要な内容
- **矛盾**: 根拠間で一致しない内容

推論には推論であることと根拠を示す。矛盾は解消根拠がある場合だけ修正し、それ以外は論点として残す。

### 4. 構成を決めて執筆する

- 冒頭で目的、対象読者、スコープ、前提を明確にする。
- 1要件・1規則・1手順を独立して参照できる粒度で記述する。
- 「適切に」「必要に応じて」など判定不能な表現を避け、主体、条件、入力、処理、出力、例外を具体化する。
- 要件は `REQ-<領域>-<連番>`、非機能要件は `NFR-<領域>-<連番>` など、文書内で一貫した識別子を付ける。
- 受入条件は観測可能な結果として記述する。実装方法を要件へ不必要に固定しない。
- 用語を統一し、既存の正本にある名称を優先する。新しい略語は初出で定義する。
- 日付、バージョン、担当者など未提供のメタデータを架空の値で埋めない。
- Mermaid や表は関係を明確にする場合だけ使用し、本文と同じ情報を重複させない。

### 5. 整合性を検証する

[quality-checklist.md](references/quality-checklist.md) を読み、該当項目を確認する。特に次を照合する。

- ユーザー依頼、要件、受入条件が相互に対応しているか
- 権限、状態遷移、正常系、異常系、境界値が抜けていないか
- UI、API、DB、ジョブ、通知、運用、セキュリティへの影響が矛盾していないか
- SQLite と PostgreSQL、PC とモバイルなど、リポジトリ固有の前提を破っていないか
- 文書内リンク、見出し、表、ファイルパス、識別子が有効か
- 実装済みと未実装、必須と任意、現在と将来が判別できるか

コードと文書に不一致があれば、ユーザーの依頼が「あるべき仕様の定義」か「現行実装の記録」かに従って扱い、残る不一致を報告する。

### 6. 差分と残課題を報告する

完了時に次を簡潔に報告する。

- 作成・更新した文書と目的
- 採用した主要な前提
- 根拠にした主要ファイル
- 未確定事項、矛盾、対象外、実装との不一致
- 実行した検証と、未実行ならその理由

文書のみの変更では、実行手順や設定変更を含まない限り `code-change-verification` を使用しない。文書がコード変更に付随する場合は、元の作業スキルとリポジトリの検証指示にも従う。

## リポジトリ固有の扱い

- ユーザー向け文書と報告を日本語で記述する。
- 機能・画面仕様の基礎は `docs/requirements.md`、デプロイの正本は `docs/deployment.md`、バックアップの正本は `docs/backup-requirements.md`、運用手順は `docs/manuals/` を優先して確認する。
- 画面案は `docs/images/`、モバイル公開側の画面案は `docs/mobile_images/` を参照する。
- UIの仕様を作成・更新する場合は、対象画面案と実装の双方を確認する。
- 実装・設定・テスト・運用の変更に伴う文書同期では、`AGENTS.md` が指定する `documentation_manager`（`.codex/agents/documentation_manager.toml`）の起動条件に従う。
- 本番DBやデプロイの記述では、開発・テスト（SQLite）と本番（PostgreSQL・Kamal accessory）の前提を区別する。デプロイの正本は `docs/deployment.md`、バックアップの正本は `docs/backup-requirements.md` とする。
