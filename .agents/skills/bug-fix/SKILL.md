不具合修正の依頼を受けた場合、このスキルの手順に従うこと。

本スキルが実行されたら、定義済みのサブエージェントを積極的に使うこと。
特に
* 設計： solution-architect
* コードレビュー: code-reviewer
* データベースレビュー : database-reviewer
* ドキュメント更新 : documentation-manager
* Railsコーディング : rails-implementer
* フロントエンドコーディング : frontend-implementer
* セキュリティレビュー : security-auditor
* テスト : test-engineer
* git, github 操作 : repository-operator
* 国際化・多言語化 : internationalization-implementer
* 翻訳完全性チェック : translation
* 画面案・スクリーンショットの参照解釈 : visual-reference-analyzer

の使用を推奨する。
他のエージェントについても必要に応じて起動して作業を進めてください。

国際化・多言語化が必要な時は internationalization スキルを使用すること。
ユーザー向け文言を変更した後は translation スキルで翻訳完全性を確認し、抜けがなくなるまで翻訳を補完すること。

## 並列実行ポリシー

独立して実行できるタスクは、サブエージェントや並列ツール呼び出しを使って**同時に実行する**こと。直列に並べるだけにしない。

- 静的解析（`bundle exec srb tc`、`bin/rubocop`、`bin/brakeman`、`bin/bundler-audit`、`bin/importmap audit`）は相互に独立しているため、**同一メッセージで複数の bash ツール呼び出し**を行って並列実行する。
- 読み取り専用のサブエージェント（bug-investigator、code-reviewer、database-reviewer、security-auditor、test-engineer の調査など）は互いに依存がなければ、**同一メッセージで複数の task ツール呼び出し**を行って並列起動する。
- 編集を伴うエージェント（rails-implementer、frontend-implementer、translation、documentation-manager など）は、**変更ファイルが重複しない場合のみ並列**可。重複する場合は直列実行とする。並列起動時は各エージェントのスコープと変更対象ファイルをプロンプトで明示する。
- テストはテストDBやブラウザ資源を共有するため、全テストとシステムテストなどの重い実行は並列にせず直列化する。
- 編集系のタスクを先に完了させ、読み取り専用のレビュー・監査は編集完了後のスナップショットに対して実行する。編集とレビューを並列にする場合は、レビュー対象ファイルが編集対象と重複しないことを確認する。
- **大規模変更のレビュー**: 変更が複数レイヤーや多数のファイルに跨る場合は、役割・関心ごとにレビュー担当を分割して**同一メッセージで並列起動**する（例: 全体・統合観点は code-reviewer、DBは database-reviewer、セキュリティは security-auditor、UIは frontend-implementer 系）。ただし、ファイル間のインターフェイス不一致・重複コード・命名揺れ・横断的な問題（N+1等）を見る**統合観点のレビューを必ず1件残す**こと。指摘の重複・矛盾・誤検知はオーケストレータが突き合わせて解消する。変更が小規模な場合は分割せず1エージェントにまとめる。
- **ドキュメント同期の分担**: 対象文書が複数ある場合は文書単位で分担して並列起動する。**同一ファイルを複数エージェントに編集させない**（1文書内は1エージェント）。編集はコード変更が完了した最終スナップショットに対して行う。
- **システムテスト実行中の並列化**: システムテストは待ち時間が長いため、その実行中に読み取り専用のレビュー・監査（code-reviewer、security-auditor、database-reviewer 等）、機密情報スキャン、ドキュメント同期、翻訳の検出を**同一メッセージで並列起動**してよい（システムテストの bash は timeout を十分長く設定する）。ただし、実行中のサブエージェントにテスト・静的解析・ビルドを実行させない（CPU・テストDB競合によるフレーク防止）。翻訳の編集（locale ファイルの書き換え）はシステムテスト完了後に行うのを基本とし、並列で編集する場合は翻訳を検証するシステムテストを完了後に再実行する。
- **システムテスト失敗時の再検証**: システムテストが失敗して修正が入った場合、並列で得たレビュー・翻訳・ドキュメントの成果が陳腐化していないか確認し、**変更ファイルに関わる範囲だけ再検証**してから採用する（全体のやり直しはしない）。
- サブエージェントには、対象ファイル一覧・レビューまたは編集の範囲・観点をプロンプトで明示する。シェルを持たず `git diff` を実行できないエージェントがいるため、自分で差分を取得できる前提にしない。差分はオーケストレータが渡す。

**各フェーズにおいて、不具合の再現手順や期待動作・実際の動作が不明瞭な場合は、その時点でユーザーに確認し、明確にしてから次に進むこと。** 推測で修正すると原因誤認や手戻りが発生するため、不明点は必ず確認する。

## ブランチ運用フロー

コードを修正する際は、以下のフローで作業すること。

1. **ブランチ作成**: 作業開始前に `main` ブランチからトピックブランチを作成する (`git checkout -b <ブランチ名>`)。
2. **実装〜テスト〜コードレビュー〜セキュリティチェック**: 以下の各フェーズを実行する。コミットは修正の単位で行う。
3. **プッシュ**: 全フェーズ完了後、`git push origin <ブランチ名>` でリモートにプッシュする。
4. **PR作成**: `gh pr create --base main --head <ブランチ名> --title "..." --body "..."` でプルリクエストを作成する。
5. **Codexレビュー〜マージ**: 下記「完了後のフロー」に従い、Codexレビューの定期確認・指摘対応・マージ・後片付けまで進める。

## 完了後のフロー（コミット・プッシュ〜Codexレビュー〜マージ・後片付け）

検証とレビューが全て終わったら、次の順で完了処理まで進める。詳細は `.agents/skills/codex-review/SKILL.md` に従う。

1. **コミット・プッシュ**: 変更を論理単位でコミットし（コミット前に `.agents/skills/security-check/SKILL.md` の機密情報スキャンを実行）、リモートへプッシュする。PRが未作成なら作成する。その後、Codexレビュー待機ループに入る。
2. **Codexレビューの定期確認**: `.agents/skills/codex-review/SKILL.md` の手順に従い、Codexのレビューを確認する。指摘は issue comments・インラインコメント・reviews の3箇所をすべて確認する。
3. **指摘対応**: 各指摘の妥当性を検証し、妥当なものは修正 → `fix:` コミット（日本語メッセージ）→ プッシュ → 再レビュー依頼を繰り返す。妥当でない指摘は自己判断でスキップせず、理由を添えてユーザーへ報告し判断を仰ぐ。
4. **最終検証**: 妥当な指摘がなくなったら、マージ前に全テスト（UI変更がある場合はシステムテストも）を最終スナップショットで実行し、通過を確認する。失敗した場合は修正して再検証する。
5. **マージ・後片付け**: 妥当な指摘が残っていないことを確認して main へマージする。その後 main へ切り替えて `git pull origin main`、作業ブランチをローカル・リモートともに削除する。

CI確認は `.agents/skills/ci-verification/SKILL.md` に従う。

## ワークフロー概要

以下の各フェーズを順に実行する。**各フェーズの成果物がまとまった時点でユーザーに確認を求め、了承を得てから次のフェーズに進むこと。** 修正が完全でない場合は実装フェーズに戻ってループする。

```
不具合報告の内容理解
  ↓
現状調査（コード・直近変更・依存ライブラリ）
  ↓
原因の特定
  ↓
修正方針の提案
  ↓
再現テストの作成（可能な場合）
  ↓
コード修正
  ↓
[並列] 型チェック（Sorbet） / Rubocop / セキュリティスキャン
  ↓
[直列] 全テスト → システムテスト（必要な場合）
    └ 実行中に [並列] コードレビュー / セキュリティレビュー / 機密情報スキャン / ドキュメント同期 / 翻訳の検出
  ↓
[並列] 翻訳の編集・補完（システムテスト完了後）
  ↓
条件を満たすまでループ
  ↓
コミット → プッシュ → PR作成 → 報告
  ↓
Codexレビュー（定期確認・指摘対応） → マージ・後片付け
```

## フェーズ1: 不具合報告の内容理解

報告された不具合について以下の項目を整理する。不明点があればユーザーに確認すること。

- **概要**: 何が起きているか（期待動作と実際の動作の差分）
- **再現手順**: どう操作すると発生するか（環境・画面・URL・入力値・操作順序）
- **影響範囲**: どの画面・機能・ユーザーに影響があるか
- **緊急度**: どの程度早急な対応が必要か（本番停止・一部機能不可・表示のみ等）
- **該当バージョン**: 再現した環境（本番 / ステージング / ローカル、コミットハッシュ）

成果物: 上記を箇条書きでまとめたもの（ユーザーに確認すること）。特に再現手順が不明な場合は必ず確認してから次に進むこと。

---

## フェーズ2: 現状調査

### 2.1 コード調査

- 不具合に関連するファイルを特定する（該当画面のビュー、コントローラ、モデル、ヘルパー、JavaScript、CSS）
- 関連ファイルのコードを読み、ロジックを追跡する
- エラーログや例外が発生している場合は、該当スタックトレースから原因箇所を特定する

### 2.2 直近の変更調査

`git log` で直近の変更を確認し、不具合がいつから発生している可能性があるかを特定する。

```bash
# 直近のコミット履歴
git log --oneline -20

# 特定のファイルに絞った変更履歴
git log --oneline -10 -- <関連ファイル>
```

不具合の発生タイミングとコミット時期が関連しそうな場合、`git diff` や `git show` で該当コミットの変更内容を確認する。

必要に応じて `git bisect` で原因コミットを特定する。

### 2.3 依存ライブラリの調査

- 不具合に関係しそうなGemやJavaScriptライブラリを洗い出す
- 直近でバージョンアップされたライブラリがないか `Gemfile.lock` を確認する（本リポジトリは importmap + Stimulus のため Node.js ツールチェーン・`package.json` は使わない）
- 該当ライブラリのGitHubリポジトリで、最近のリリースや報告されている類似のIssue / Pull Requestを確認する
- 既知のバグや互換性問題が報告されていないか調査する

```bash
# Gemfile.lock から特定Gemのバージョン履歴を確認
grep -A 1 '<gem-name>' Gemfile.lock

# git log で Gemfile.lock の変更を確認
git log --oneline -- Gemfile.lock
```

成果物: 調査結果の整理（ファイルパス・コミットハッシュ・ライブラリバージョン・関連Issue URLを明記）

---

## フェーズ3: 原因の特定

調査結果を基に、不具合の原因を特定する。

- **直接原因**: どのコードが期待と異なる動作を引き起こしているか
- **根本原因**: なぜそのコードが書かれたか（設計の見落とし / 想定漏れ / 結合ミス / ケアレスミス等）
- **条件**: どのような条件下で発現するか（特定のデータ状態・画面幅・権限・ブラウザ等）

特定した原因をユーザーに説明し、修正方針の提案に進んで良いか確認すること。

成果物: 原因の説明（直接原因 + 根本原因 + 発現条件）

---

## フェーズ4: 修正方針の提案

原因を踏まえ、修正の方針をユーザーに提案する。

- **修正方法**: どのファイルをどう修正するか
- **影響範囲**: 修正による他の機能への影響
- **代替案（ある場合）**: 複数の修正方法が考えられる場合、それぞれのトレードオフを説明する
- **テスト方針**: どのようなテストで再現および修正を確認するか

成果物: 修正方針の説明（ユーザー確認済み）。確信が持てない場合は複数案を提示し、ユーザーに選んでもらうこと。
修正内容が自明な場合はユーザーに確認せずに進んでよい。

---

## フェーズ5: 再現テストの作成

可能な場合、不具合を再現するテストを先に作成する（テスト駆動）。これにより修正の正当性を検証できるだけでなく、今後再び同じ不具合が再発することを防止する。

- 本リポジトリは `test/integration/blog_flow_test.rb` にアサーションが集中するため、原則として該当ファイルに再現テストを追加する
- モデル固有の不具合は `test/models/` の該当ファイルに追加する
- `AdminUser` を作成する際は `password_salt:` と `password_digest: AdminUser.digest_password(...)` を渡すこと（`password=` セッターは salt を再生成するためセットアップでは使いづらい）
- Markdown の表示不具合は `MarkdownRenderer` と `PostsHelper#render_markdown` / `#extract_headings` 経由で再現すること（コントローラーやビューから直接レンダリングしない）

テスト作成後、**修正前の状態でテストが失敗することを確認** すること（これによりテストが不具合を正しく捉えていることを確認する）。

例：
```bash
bin/rails test test/integration/blog_flow_test.rb -n test_name
```

成果物: 追加したテストコード。修正前にテストが失敗することの確認結果。

---

## フェーズ6: コード修正

修正方針に従ってコードを修正する。

- 修正は最小限にとどめ、不要な変更を加えない
- 既存のコーディングパターンに従う
- Markdown を扱う場合は `MarkdownRenderer` + `PostsHelper` 経由とし、コントローラーやビューから直接レンダリングしない
- 修正後に `bin/rails test` で全テストがパスすることを確認する
- エッジケース（空データ・nil・権限不足等）を考慮する

---

## フェーズ7: 静的解析・テスト

7.1〜7.3 の静的解析は相互に独立しているため、同一メッセージで複数の bash ツール呼び出しを行い並列実行する。7.4 の全テストと 7.5 のシステムテストはテストDBを共有するため並列にせず、7.4 → 7.5 の直列で実行する。待ち時間が長い 7.5 の実行中は、7.6 の翻訳の検出、7.7 のドキュメント同期、フェーズ8.2のレビュー、フェーズ9の機密情報スキャンを同一メッセージで並列起動してよい（翻訳の編集は 7.5 完了後）。実行中のサブエージェントにテスト・静的解析・ビルドを実行させないこと。システムテストが失敗して修正が入った場合は、並列で得た成果を変更ファイルに関わる範囲だけ再検証してから採用する。

### 7.1 型チェック（Sorbet）

RubyまたはRBIを変更した場合に実行する。Gem依存を変更した場合は先に `bin/tapioca gem`、Rails DSL に由来する型情報を変更した場合は先に `bin/tapioca dsl` を実行し、生成RBIを同期する。

```bash
bundle exec srb tc
```

モデル・コントローラを修正した場合は、型エラーが発生していないか確認すること。`# typed: true` 以上のファイルで新たなエラーが出た場合は、シグネチャ追加または `T.unsafe` / `T.let` で対処すること。

### 7.2 Rubocop

```bash
bin/rubocop
```

指摘がある場合は修正すること。

### 7.3 セキュリティスキャン

```bash
bin/brakeman --no-pager
bin/bundler-audit
```

importmap・JavaScript 依存を変更した場合は `bin/importmap audit` も実行する。

### 7.4 全テスト実行

```bash
bin/rails test
```

既存テストが全てパスすることを確認する。追加した再現テストがパスすることも確認する。

### 7.5 システムテスト（必要な場合のみ）

```bash
bin/rails test:system
```

ブラウザ駆動のテストが必要な修正の場合のみ実行する。

### 7.6 翻訳完全性チェック

ユーザー向け文言、locale ファイル、ビュー、flash、バリデーション、メール、ジョブ、通知、JavaScript を変更した場合は、translation スキルの手順に従い、translation エージェントを起動して翻訳完全性を確認する。

1. 全対象localeファイル間で翻訳キーの欠落をチェックする。
2. 直書きのユーザー向け文言が残っていないか検索する。
3. 未翻訳キー・直書き文言があれば translation エージェントに翻訳補完を委譲する。
4. 補完後、再度 1〜2 を実行し、未翻訳がなくなるまで繰り返す。
5. 翻訳の変更によって既存テストが壊れていないか、関連テストを実行する。

### 7.7 ドキュメント同期

修正が `docs/` 以下の仕様書・README・デプロイ・運用文書に影響する場合は、差分と根拠を添えて documentation-manager を起動し、ドキュメントを同期する。対象文書が複数ある場合は文書単位で分担して並列起動してよい（同一ファイルを複数エージェントに編集させない）。翻訳補完（7.6）と変更ファイルが重複しない場合は並列起動してよい（重複する場合は直列）。監査のみを依頼する場合は先に差分と根拠の報告を受けたうえで、更新の明示委譲を行ってから編集させる。

## フェーズ8: コードレビュー（別エージェント依頼含む）

### 8.1 自己レビュー

以下の観点で自身の修正をレビューする。

- **修正の正確性**: 原因に対して正しい修正が行われているか
- **エッジケース**: 境界値・異常値・nil・空データで破綻しないか
- **エラーハンドリング**: 想定外の入力や状態で適切に動作するか
- **N+1**: データベースクエリにN+1が発生していないか
- **セキュリティ**: SQLインジェクション、XSS、CSRFの対策ができているか
- **既存コードとの一貫性**: 同じ問題に対して同じパターンで解決しているか
- **CSSクラス名**: 既存の命名規則に従っているか
- **JavaScript**: Stimulus コントローラの規則に従っているか

### 8.2 別エージェントへのレビュー依頼

task ツールを使用して code-reviewer にコードレビューを依頼する。認証認可・入力処理・SQL・アップロード・機密情報などセキュリティに関係する修正では、security-auditor も**同一メッセージで並列起動**する。変更が複数レイヤーに跨る場合は database-reviewer などの担当も加えて役割分担するが、統合観点のレビューは必ず1件残すこと。依頼時は以下の情報を含めること。

```markdown
依頼内容: 不具合修正のコードレビュー
修正ファイル: <ファイルパスのリスト>
修正内容: <修正の概要>
確認観点:
1. 修正が原因を正しく解決しているか
2. エッジケースや副作用の見落としがないか
3. 既存コードのパターンと一貫性があるか
4. 改善すべき箇所があるか
```

レビュー結果を受け取ったら、指摘事項を確認し、対応が必要な場合はフェーズ6（コード修正）に戻る。修正が入った場合は、翻訳完全性チェック（7.6）とドキュメント同期（7.7）の再実行が必要か確認する。

## フェーズ9: セキュリティチェック

`git commit` を実行する前に必ず `.agents/skills/security-check/SKILL.md` の手順に従い、コミット対象の変更ファイルを対象とした機密情報スキャンを実行すること。リポジトリ全体のスキャンはユーザーが明示的に指定した場合のみ実行すること。

読み取り専用のためフェーズ8.2のレビューと並列に実行してよいが、フェーズ6に戻る修正が入った場合は再実行すること。

- 🔴 CRITICAL または 🟠 HIGH の指摘が見つかった場合はコミットを中断し、ユーザーに報告して指示を仰ぐこと
- 🟡 MEDIUM 以下の指摘のみの場合は報告を行うが、ユーザーの判断でコミットを継続してよい

## フェーズ10: 修正完了ループ

全テストがパスし、コードレビュー・セキュリティチェックが完了した後、不具合報告の内容と突き合わせて修正が完了しているか確認する。

未完了の場合はフェーズ6（コード修正）に戻り、修正 → テスト → レビュー → セキュリティチェックのサブループを回す。ループの各周回で不明点があればユーザーに質問すること。

## フェーズ11: コミット・報告・CI確認

```bash
git add <該当ファイル>
git commit -m "{日本語のコミットメッセージ}"
git push
```

コミットメッセージは以下の形式を推奨する:

```
fix: 不具合の概要（原因と修正方法を簡潔に）

- 原因: xxx
- 修正: xxx
```

**CI確認**: CI は `main` への push 時のみ実行されるため、PRブランチでは確認できない。main へのマージ後に `.agents/skills/ci-verification/SKILL.md` の手順に従い CI を確認する。CIが失敗した場合は同スキルに従い修正ループを回す。

CI確認後、以下の内容をユーザーに日本語で報告する:

- 不具合の原因
- 実施した修正内容
- 変更したファイルのリスト
- （必要な場合）動作確認方法や注意点
- コードレビューでの指摘事項と対応（あった場合）
- CIの確認結果（PRブランチではCIは実行されないため、mainマージ後に確認する旨）
- 残課題（未対応・既知の問題・フォローアップが必要な点があれば）
- PRのURL

その後、「完了後のフロー」に従い、Codexレビューの定期確認・妥当な指摘への対応・指摘がなくなった後のmainへのマージ・後片付けまで進める。
