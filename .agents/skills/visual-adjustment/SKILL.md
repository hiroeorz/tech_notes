画面の見た目（CSS / レイアウト / 余白 / 色 / フォント / テーマ / レスポンシブ崩れ等）の調整依頼を受けた場合、このスキルの手順に従うこと。新規画面、既存画面のリデザイン、レイアウト・余白・色・文字・テーマ・レスポンシブ崩れ・アクセシビリティの改善を含む。

**各フェーズにおいて、依頼内容やデザインの意図で不明瞭な点があれば、その時点でユーザーに確認し、明確にしてから次に進むこと。すべてのユーザー向けメッセージ・完了報告・コミットメッセージは日本語で記述すること。**

## 基本方針

- ユーザーの明示的な要件を最優先し、次に `docs/images/`（モバイルは `docs/mobile_images/`）、`docs/requirements.md` セクション3–9、既存コードの順で根拠を確認する。
- 仕様書に記載された将来要件を、実装済みの画面や挙動として扱わない。画面案にない挙動を画面案だけから発明しない。
- 画面上の表示制御を認証・認可の代替にしない。権限に関わる変更はサーバー側の認可（`Admin::BaseController#require_admin` 等）も確認する。
- 既存のデザイントークン、CSS カスタムプロパティ（`var(--paper)`、`var(--ink)`、`var(--orange)`、`var(--display)`、`var(--sans)`、`var(--mono)` 等）、コンポーネント、命名規則（kebab-case）を優先し、同じ意味の値やパターンを重複させない。
- importmap + Stimulus の構成を維持し、Node.js ツールチェーンや新しい UI ライブラリを独断で導入しない。JS は `app/javascript/` に配置し、pinning は `config/importmap.rb` で行う。
- デザイン意図、対象画面、対象ユーザー、対応デバイスが結果を左右する場合は、実装前に不明点を整理して確認する。

## 並列実行ポリシー

独立して実行できるタスクは、サブエージェントや並列ツール呼び出しを使って**同時に実行する**こと。直列に並べるだけにしない。

- 静的解析（`bundle exec srb tc`、`bin/rubocop`、`bin/brakeman`、`bin/bundler-audit`）や資料・コードの調査は相互に独立しているため、**同一メッセージで複数の bash ツール呼び出し**を行って並列実行する。
- 読み取り専用のサブエージェント（`solution_architect`、`code_reviewer`、`security_auditor`、`test_engineer` の調査など）は互いに依存がなければ、**同一メッセージで複数の task ツール呼び出し**を行って並列起動する。
- 編集を伴うエージェント（`frontend_implementer`、`documentation_manager`、`translation` など）は、**変更ファイルが重複しない場合のみ並列**可。重複する場合は直列実行とする。並列起動時は各エージェントのスコープと変更対象ファイルをプロンプトで明示する。
- ブラウザ検証・システムテストはブラウザ資源とテスト DB を共有するため、重い実行は並列にせず直列化する。
- 編集系のタスクを先に完了させ、読み取り専用のレビュー・監査は編集完了後のスナップショットに対して実行する。編集とレビューを並列にする場合は、レビュー対象ファイルが編集対象と重複しないことを確認する。
- **大規模変更のレビュー**: 変更が複数画面・複数レイヤーや多数のファイルに跨る場合は、役割・関心ごとにレビュー担当を分割して**同一メッセージで並列起動**する（例: 全体・統合観点は `code_reviewer`、セキュリティは `security_auditor`、アクセシビリティやレスポンシブは `frontend_implementer` 系）。ただし、ファイル間のインターフェイス不一致・重複コード・命名揺れ・横断的な問題を見る**統合観点のレビューを必ず1件残す**こと。指摘の重複・矛盾・誤検知はオーケストレータが突き合わせて解消する。変更が小規模な場合は分割せず1エージェントにまとめる。
- **ドキュメント同期の分担**: 対象文書が複数ある場合は文書単位で分担して並列起動する。**同一ファイルを複数エージェントに編集させない**（1文書内は1エージェント）。編集は UI 変更が完了した最終スナップショットに対して行う。
- **ブラウザ検証・システムテスト実行中の並列化**: 待ち時間が長いため、その実行中に読み取り専用のレビュー・監査（`code_reviewer`、`security_auditor` 等）、機密情報スキャン、ドキュメント同期、翻訳の検出を**同一メッセージで並列起動**してよい（bash の timeout を十分長く設定する）。ただし、実行中のサブエージェントにテスト・静的解析・ビルドを実行させない（CPU・テスト DB 競合によるフレーク防止）。翻訳の編集（locale ファイルの書き換え）はブラウザ検証・システムテスト完了後に行うのを基本とし、並列で編集する場合は翻訳を検証するシステムテストを完了後に再実行する。
- **ブラウザ検証・システムテスト失敗時の再検証**: 失敗して修正が入った場合、並列で得たレビュー・翻訳・ドキュメントの成果が陳腐化していないか確認し、**変更ファイルに関わる範囲だけ再検証**してから採用する（全体のやり直しはしない）。
- サブエージェントには、対象ファイル一覧・レビューまたは編集の範囲・観点をプロンプトで明示する。シェルを持たず `git diff` を実行できないエージェントがいるため、自分で差分を取得できる前提にしない。

## 役割分担

このスキルはデザイン判断と検証の手順を提供する。実装の担当は次のように分ける。

- UI コードの実装を委譲する場合は `frontend_implementer` を使う。
- 画面をまたぐ設計や責務分割が必要な場合は `solution_architect` に相談する。
- 実装後の差分確認は `code_reviewer`、セキュリティ確認は `security_auditor`、テスト追加は `test_engineer` に委譲する。
- 仕様書や画面案の同期が必要な場合は `documentation_manager` に根拠とともに委譲する。
- ユーザー向け文言を変更した場合は `translation` に委譲する。
- これらの委譲は親エージェントが明示的に行い、エージェント同士で同じファイルを並列編集しない。
- 読み取り専用の確認（レビュー・監査・調査）は相互に依存がなければ並列起動してよい（並列実行ポリシー参照）。

```
  ↓

  ↓

```

## フェーズ1: 依頼内容の把握

以下の項目を整理する。不明点があればユーザーに確認すること。

- **調整箇所**: どの画面・コンポーネントのどこを調整するか
- **期待する見た目**: 具体的にどう変えたいか（色・サイズ・位置・余白・表示・非表示等）
- **参考画像**: スクリーンショットやデザインカンプがあればパスを確認する
- **現状の課題**: 現状で何が問題か（デザインイメージと異なる / 表示崩れ / 見づらい等）
- **関連デザイン要件**: `docs/requirements.md` セクション3–9の該当セクション番号
- **対象デバイス・状態**: PC / タブレット / スマートフォンの幅、フォーム・空状態・ローディング・エラー・権限別表示の別

成果物: 上記を箇条書きでまとめたもの（ユーザーに確認すること）。見た目だけでは決まらない業務挙動、権限、文言、状態遷移がある場合は、推測で確定せずユーザーまたは親エージェントへ確認する。

## フェーズ2: デザイン要件の確認

### 2.1 要件書の確認

`docs/requirements.md` セクション3–9の該当セクションを読み、デザインの仕様・意図を把握する。対象画面に関係する資料だけを読み、根拠と実装済み範囲を区別する。

### 2.2 デザイン画像の確認

`docs/images/` または `docs/mobile_images/` に対象画面の参照画像がないか確認する。`docs/images/` に画像がある場合は画像を目視し、以下の観点で現状との差異を特定する:

- 情報の優先順位と視線誘導
- 色味（アクセントカラー `var(--orange)` の使用箇所）
- フォント（`var(--display)` 明朝、`var(--sans)` ゴシック、`var(--mono)` 等幅）
- 色、コントラスト、背景、境界線、影
- 余白・配置、グリッド、コンポーネント間の一貫性
- アイコンの有無と種類
- ボタン、リンク、フォーム部品
- PC からモバイルへの構造変化、レスポンシブ時のレイアウト
- テーマ（light/dark）ごとの見た目

成果物: 「デザイン要件」と「現状との差分」の2つに分けた差異リスト。

---

## フェーズ3: 現状コードの調査

### 3.1 CSSの調査

- 対象画面に関連する CSS を特定する（`app/assets/stylesheets/application.css` に全 CSS が集約されているため、まず同ファイルを確認する。該当ビューの inline style / `<style>` タグも確認）
- CSS カスタムプロパティ（`var(--paper)`, `var(--ink)`, `var(--orange)` 等）の使用状況を確認する
- テーマ切り替え（`.theme-dark`）対応の有無を確認する（切替クラスは `app/javascript/application.js` でトグルされる）
- 既存のセレクタ命名パターン（kebab-case）、ブレークポイント、CSS の優先順位・継承・セレクタの影響範囲を確認する

### 3.2 ビュー・パーシャルの調査

- 対象画面の ERB ファイルを確認する
- 公開レイアウト（`layouts/application.html.erb`）とパーシャル（`shared/_header.html.erb`、`shared/_sidebar.html.erb`）が唯一のレイアウト構成であり、Admin ビュー（`app/views/admin/`）も同じレイアウトを再利用する（admin 専用レイアウトなし）ことを前提に、共通パーシャルの影響を確認する
- HTML 構造と CSS クラスの付与状況を確認する。HTML 構造を変えたときの既存スタイル・既存テストへの影響を確認する

### 3.3 Stimulus コントローラの調査

- 動的な表示制御（タブ切り替え、モーダル開閉、プレビュー等）に関わる JavaScript の動作を確認する
- `app/javascript/controllers/` 以下の該当コントローラを確認する（初期表示・動的状態・エラー・無効化・キーボード操作を含む）
- 既存のシステムテスト（`test/system/`）、アクセシビリティ関連のテストを確認する

成果物: 関連ファイルのパス一覧と現状の構造メモ。

## フェーズ4: デザイン方針・修正方針の決定

調査結果を基に、実装前に必要な範囲でデザイン方針を定義する。

- **情報設計**: 情報の優先順位とセマンティックな HTML 構造、見出し階層
- **コンポーネント責務**: 再利用単位、状態一覧（通常・空・ローディング・エラー・無効・権限別・テーマ別）、ERB・CSS・Stimulus の変更方針と影響範囲
- **トークン**: 色・文字・間隔・角丸・境界線・影などのデザイントークン。既存トークンを再利用し、必要なら意味が明確なトークンを追加する
- **レスポンシブ**: 画面幅ごとのレイアウト、折り返し、表示・非表示、タッチ領域。既存のブレークポイントに従う
- **アクセシビリティ**: キーボード操作、フォーカス表示、ラベル、見出し構造、代替テキスト、コントラスト
- **変更方針**: どのファイルをどう変更するか（CSS 変数の変更、セレクタ追加、クラス名変更、HTML 構造変更等）、修正による他の画面・コンポーネントへの波及、確認方法
- **デザイン案との差異**: デザイン案と実装が異なる場合の採用理由と未確定事項

複数案がある場合は、見た目だけでなく保守性、既存画面との一貫性、レスポンシブ性、アクセシビリティを比較する。確信が持てない場合は複数案を提示し、ユーザーに選んでもらうこと。設計のみを依頼された場合は、この方針と受入条件を成果物として提示し、コード編集へ進まない。

成果物: デザイン方針・修正方針の説明（ユーザー確認済み）。

## フェーズ5: コード修正

修正方針に従ってコードを修正する。実装を行う場合は、設計方針を `frontend_implementer` へ明示的に委譲するか、親エージェントが担当する。複数チケットへ分割して委譲する場合は、**変更ファイルが重複しない範囲で同一メッセージから並列起動**してよい（重複する場合は直列。並列実行ポリシー参照）。

### 5.1 CSS 修正時の注意点

- `app/assets/stylesheets/application.css` に全 CSS が集約されているため、変更箇所が散らばらないようにする。CSS は責務のある場所にまとめ、過度なセレクタの強制や場当たり的な上書きを避ける
- 色や間隔は既存トークン（`var(--orange)` 等）を再利用し、必要なら意味が明確なトークンを追加する。生の色コードを直接書かない
- テーマ（`.theme-dark`）対応が必要な場合は、必ず両方のテーマで崩れがないことを確認する
- レスポンシブ対応（メディアクエリ）が必要な箇所は、既存のブレークポイントに従う

### 5.2 ERB 修正時の注意点

- HTML 構造を変更する場合、既存の CSS セレクタが効かなくなる可能性があるため、影響範囲を確認する。セマンティクスと既存のテスト・スタイルへの影響を確認して変更する
- 新たに追加する CSS クラス名は既存の命名規則（kebab-case）に従う
- 仕様書や画面案の編集は、同期が依頼範囲に含まれる場合だけ行う

### 5.3 Stimulus 修正時の注意点

- 状態を明示的に管理し、初期表示、エラー、無効化、キーボード操作を含めて確認する

### 5.4 テーマ対応

- ライトテーマの調整が完了したら、`.theme-dark` での見た目も確認し、調整が必要であれば同様に対応する

## フェーズ6: ブラウザ確認

`.opencode/skills/browser-check/SKILL.md`（browser-check スキル）の手順に従い、ブラウザでの表示確認を行う。利用可能なブラウザ操作またはシステムテストで、少なくとも次を確認する。

### 6.1 確認項目

- デスクトップ幅（1280x720）での表示崩れがないか（画面案との比較では対象幅を記録する）
- モバイル幅（375x812）での表示崩れがないか。必要に応じてタブレット幅も確認する
- 指定されたデザイン要件を満たしているか（`docs/images/*.png`、`docs/mobile_images/*` との照合）
- 通常、空、ローディング、エラー、無効、権限別、テーマ別の状態が適切か
- キーボード操作、フォーカス表示、フォームラベル、見出し階層、alt属性、ARIA、コントラスト比が適切か
- 横スクロール、文字の欠落・重なり、長文・大きな入力値、タップ領域に問題がないか
- コンソールエラーが出ていないか
- ネットワークエラーが出ていないか
- Stimulus の動的状態が正常か
- ライトテーマ / ダークテーマの両方で正常か
- フォームやインタラクション要素の見た目が適切か

スクリーンショットを取得できる場合は、対象幅を記録して比較結果に添える。

### 6.2 問題発見時の対応

確認で問題が見つかった場合はフェーズ5（コード修正）に戻る。原因を CSS の優先順位・継承、メディアクエリ、HTML 構造、Stimulus の状態管理に分解して修正し、再確認する:

- CSS セレクタの優先度・継承による効き漏れ
- メディアクエリの適用条件
- JavaScript による動的なクラス付与前の初期状態
- テーマ切り替え時の CSS 変数の未定義

## フェーズ7: 静的解析・テスト

ERB、CSS、Stimulus、ヘルパーを変更した場合は、`.agents/skills/code-change-verification/SKILL.md` を読み、変更内容に応じて関連テスト、システムテスト、`bin/rubocop` などを実行する。ブラウザや Chromium が使えない場合は、未実行理由と代替確認を報告する。

実行順序は次のとおり。静的解析（`bundle exec srb tc`、`bin/rubocop`、`bin/brakeman`、`bin/bundler-audit`）は相互に独立しているため、**同一メッセージで複数の bash ツール呼び出し**を行って並列実行する。全テストとシステムテストはテスト DB・ブラウザ資源を共有するため直列化する。

```text
[並列] 型チェック / Rubocop / セキュリティスキャン（Brakeman・bundler-audit）
  ↓
[直列] 全テスト → システムテスト（ブラウザ検証を含む）
    └ 実行中に [並列] コードレビュー / セキュリティレビュー / 機密情報スキャン / ドキュメント同期 / 翻訳の検出
```

ブラウザ検証やシステムテストは待ち時間が長いため、その実行中に読み取り専用タスク（レビュー・監査・機密情報スキャン・ドキュメント同期・翻訳の検出）を同一メッセージで並列起動してよい（翻訳の編集は完了後。並列実行ポリシー参照）。実行中のサブエージェントにテスト・静的解析・ビルドを実行させないこと。システムテストが失敗して修正が入った場合は、並列で得た成果を変更ファイルに関わる範囲だけ再検証してから採用する。

### 7.1 Rubocop

```bash
bin/rubocop
```

### 7.2 全テスト

```bash
bin/rails test
```

CSS のみの変更であればテストへの影響は通常ないが、ERB・Stimulus・ヘルパーを変更した場合は必ず実行する。ユーザー向け文言を変更した場合は、全対応 locale の翻訳完全性を確認する。画面変更で仕様書との同期が必要な場合は、変更根拠と対象ファイルを `documentation_manager` へ渡す。

### 7.3 サブエージェントによるレビュー・セキュリティチェック

編集完了後のスナップショットに対し、Task tool で `code_reviewer`（差分確認）と `security_auditor`（セキュリティ監査）を起動する。依頼には変更ファイル、変更概要、確認済みのテスト結果を含め、特に以下を確認させる:

- ERB や Markdown 表示に XSS のリスクがないか
- フォームや Stimulus の変更で CSRF 対策や入力処理を弱めていないか
- 外部 URL、画像、アップロードを扱う変更に安全性の問題がないか
- 認証済みユーザー向け要素の表示条件や管理画面の認可を崩していないか（表示制御を認可の代替にしていないか）
- 機密情報や個人情報を CSS、ERB、JavaScript、スクリーンショットへ混入していないか

Critical または High の指摘がある場合は完了扱いにせず、フェーズ5（コード修正）へ戻る。Medium 以下の指摘も内容を確認し、対応しない場合は理由を完了報告に記載する。

---

## フェーズ8: 修正完了・報告

以下を日本語で簡潔に報告する:

- デザイン上の判断と実装・調整内容
- 変更ファイルと、仕様・画面案（`docs/requirements.md` セクション番号、`docs/images/` / `docs/mobile_images/`）との対応
- 対応した画面幅・状態・アクセシビリティ項目
- 実行したテスト、リンター、ブラウザ確認と結果
- 未実行の確認、未確定事項、残存リスク

---

## フェーズ9: 完了後のフロー（コミット・プッシュ・PR作成〜Codexレビュー〜マージ・後片付け）

検証とレビューが全て終わったら、次の順で完了処理まで進める。

### 9.1 ブランチ確認

現在のブランチが `main` から派生したトピックブランチであることを確認する。

```bash
git branch --show-current
```

### 9.2 機密情報スキャン

コミット前に `.agents/skills/security-check/SKILL.md` の手順に従い、コミット対象の変更ファイルを対象とした機密情報スキャンを実行する（リポジトリ全体のスキャンはユーザーが明示的に指定した場合のみ）。

- 🔴 CRITICAL または 🟠 HIGH の指摘がある場合はコミットを中断し、ユーザーに報告して指示を仰ぐ

### 9.3 コミット

```bash
git add <該当ファイル>
git commit -m "{日本語のコミットメッセージ}"
```

コミットメッセージは日本語で、以下の形式を推奨する:

```
feat: 調整内容の概要

- 変更1
- 変更2
```

### 9.4 プッシュ

```bash
git push origin <ブランチ名>
```

### 9.5 PR作成

```bash
gh pr create --base main --head <ブランチ名> --title "..." --body "..."
```

PRの説明には以下の内容を含める:

- 調整の目的と概要
- 変更したファイルのリスト
- デザイン要件との対応（該当する要件セクション番号）
- 確認したチェック項目と結果
- 残課題（ある場合）
- スクリーンショット（あれば。対象幅を記録する）

### 9.6 Codexレビュー・マージ・後片付け

PR 作成後は Codex レビュー（codex-review）を参照してレビューを確認し、妥当な指摘は修正 → `fix:` コミット（日本語メッセージ）→ プッシュ → 再レビュー依頼を繰り返す。妥当でない指摘は自己判断でスキップせず、理由を添えてユーザーへ報告し判断を仰ぐ。妥当な指摘が残っていないことを確認して main へマージし、その後 main へ切り替えて `git pull origin main`、作業ブランチをローカル・リモートともに削除する。

### 9.7 報告

作成した PR の URL をユーザーに伝え、レビューを依頼する。マージ・後片付けまで行った場合は、マージ結果とブランチ削除結果も報告する。
