Railsのバージョンアップ（例: 8.1.x → 8.2.x または 9.0.x）を実施する場合、このスキルの手順に従うこと。

本スキルが実行されたら、定義済みのサブエージェントを積極的に使うこと。
特に
* 設計: solution_architect
* コードレビュー: code_reviewer
* データベースレビュー: database_reviewer
* ドキュメント更新: documentation_manager
* Railsコーディング: rails_implementer
* フロントエンドコーディング: frontend_implementer
* セキュリティレビュー: security_auditor
* テスト: test_engineer
* git, github 操作: repository_operator
* 原因調査: bug_investigator

の使用を推奨する。
他のエージェントについても必要に応じて起動して作業を進めること。
各サブエージェントが使用するLLMモデルについては、各サブエージェントで定義されているモデルを使用すること。

ユーザー向け文言を追加・変更する場合は `.agents/skills/translation/SKILL.md`（必要に応じて `.agents/skills/internationalization/SKILL.md`）に従うこと。

## 並列実行ポリシー

独立して実行できるタスクは、サブエージェントや並列ツール呼び出しを使って**同時に実行する**こと。直列に並べるだけにしない。

- 静的解析（`bundle exec srb tc`、`bin/rubocop`、`bin/brakeman --no-pager`、`bin/bundler-audit`、`bin/importmap audit`）やリサーチ（リリースノート・gem整合性・非推奨警告・アプリコード影響調査）は相互に独立しているため、**同一メッセージで複数の bash ツール呼び出し／task 呼び出し**を行って並列実行する。
- 読み取り専用のサブエージェント（solution_architect、code_reviewer、database_reviewer、security_auditor、bug_investigator、test_engineer の調査など）は互いに依存がなければ、**同一メッセージで複数の task ツール呼び出し**を行って並列起動する。
- 編集を伴うエージェント（rails_implementer、frontend_implementer、translation、documentation_manager など）は、**変更ファイルが重複しない場合のみ並列**可。重複する場合は直列実行とする。並列起動時は各エージェントのスコープと変更対象ファイルをプロンプトで明示する。
- テストはテストDBやブラウザ資源を共有するため、全テストとシステムテストなどの重い実行は並列にせず直列化する。
- 編集系のタスクを先に完了させ、読み取り専用のレビュー・監査は編集完了後のスナップショットに対して実行する。編集とレビューを並列にする場合は、レビュー対象ファイルが編集対象と重複しないことを確認する。
- **大規模変更のレビュー**: 変更がアプリコード・`config/`・`Gemfile`・Dockerfile・ドキュメントなど多数のファイルに跨る場合は、役割・関心ごとにレビュー担当を分割して**同一メッセージで並列起動**する（例: 全体・統合観点は code_reviewer、DBは database_reviewer、セキュリティは security_auditor）。ただし、ファイル間のインターフェイス不一致・重複コード・命名揺れ・横断的な問題を見る**統合観点のレビューを必ず1件残す**こと。指摘の重複・矛盾・誤検知はオーケストレータが突き合わせて解消する。変更が小規模な場合は分割せず1エージェントにまとめる。
- **ドキュメント同期の分担**: 対象文書（`README.md`、`AGENTS.md`、`docs/` 配下）が複数ある場合は文書単位で分担して並列起動する。**同一ファイルを複数エージェントに編集させない**（1文書内は1エージェント）。編集はコード変更が完了した最終スナップショットに対して行う。
- **最終確認・システムテスト・デグレーションチェック実行中の並列化**: システムテストやデグレッションチェック（アプリ起動確認）は待ち時間が長いため、その実行中に読み取り専用のレビュー・監査、機密情報スキャン、ドキュメント同期、翻訳の検出を**同一メッセージで並列起動**してよい。ただし、実行中のサブエージェントにテスト・静的解析・ビルドを実行させない（CPU・テストDB競合によるフレーク防止）。翻訳の編集（locale ファイルの書き換え）は完了後に行うのを基本とし、並列で編集する場合は翻訳を検証するシステムテストを完了後に再実行する。
- **失敗時の再検証**: テストやデグレッションチェックが失敗して修正が入った場合、並列で得たレビュー・翻訳・ドキュメントの成果が陳腐化していないか確認し、**変更ファイルに関わる範囲だけ再検証**してから採用する（全体のやり直しはしない）。
- サブエージェントには、対象ファイル一覧・レビューまたは編集の範囲・観点をプロンプトで明示する。シェルを持たず `git diff` を実行できないエージェントがいるため、自分で差分を取得できる前提にしない。

## ブランチ運用フロー

コードを修正する際は、以下のフローで作業すること。

1. **ブランチ作成**: 作業開始前に `main` ブランチからトピックブランチを作成する (`git checkout -b <ブランチ名>`)。
2. **実装〜テスト〜コードレビュー〜セキュリティチェック**: 以下の各フェーズを実行する。コミットは修正の単位で行う。
3. **プッシュ**: 全フェーズ完了後、`git push origin <ブランチ名>` でリモートにプッシュする。
4. **PR作成**: `gh pr create --base main --head <ブランチ名> --title "..." --body "..."` でプルリクエストを作成する。
5. **Codexレビュー〜マージ**: 下記「完了後のフロー」に従い、Codexレビューの定期確認・指摘対応・最終検証・マージ・後片付け・ノウハウ保存まで進める。

## 完了後のフロー（コミット・プッシュ〜Codexレビュー〜マージ・後片付け〜ノウハウ保存）

検証とレビューが全て終わったら、次の順で完了処理まで進める。詳細は `.agents/skills/codex-review/SKILL.md` と `.agents/skills/save-memory-knowhow/SKILL.md` に従う。

1. **コミット・プッシュ**: 変更を論理単位でコミットし（コミット前に `.agents/skills/security-check/SKILL.md` の手順に従い**コミット対象の変更ファイル**を対象とした機密情報スキャンを実行）、リモートへプッシュする。PRが未作成なら作成する。**PR作成直後に、WSLで実行するデプロイコマンド（`kamal deploy`）をユーザーへ提示**してから、Codexレビュー待機ループに入る（エージェントはデプロイを実行しない。詳細は `.opencode/skills/deploy-request/SKILL.md`。本番反映の標準はマージ後で、PRブランチをデプロイする場合はWSLでそのブランチを checkout する必要がある旨を添える）。修正push後は最新SHAで再提示する。
2. **Codexレビューの定期確認**: PR作成後の Codex の自動レビューを確認する。初回はPR作成時に自動で付くことが多い。付かない場合や修正 push 後の再レビューは `@codex レビューお願い` を明示投稿する。指摘は issue comments・インラインコメント・reviews の各箇所を確認する。
3. **指摘対応**: 各指摘の妥当性を検証し、妥当なものは修正 → `fix:` コミット（日本語メッセージ）→ プッシュ → 再レビュー依頼を繰り返す。各修正ラウンドの検証は変更範囲の関連テストと静的解析のみとし、全テスト・システムテストは修正がすべて完了した最終スナップショットで1回だけ実行する。妥当でない指摘は自己判断でスキップせず、理由を添えてユーザーへ報告し判断を仰ぐ。
4. **最終検証**: 妥当な指摘がなくなったら、マージ前にフェーズ7の最終確認（全テスト・システムテスト等）を最終スナップショットで再実行し、通過を確認する。失敗した場合は修正して再検証する。
5. **マージ・後片付け**: 妥当な指摘が残っていないことを確認して main へマージする（マージコミット方式）。その後 main へ切り替えて `git pull origin main`、作業ブランチをローカル・リモートともに削除する。**後片付け完了後、マージコミットの完全SHAを使ったデプロイ手順（`git pull` + `kamal deploy`）をユーザーへ提示**する（エージェントは実行しない）。
6. **ノウハウ保存**: マージ後、`.agents/skills/save-memory-knowhow/SKILL.md` に従い、今回のプロセスで苦戦した点・試行錯誤で分かったこと・次の担当者に伝えるべき知見が**あれば** `~/ai-memory` へ追記する（アプリ固有情報は含めない）。

CI確認は `.agents/skills/ci-verification/SKILL.md` に従う。

## ワークフロー概要

```
リサーチ（リリースノート・破壊的変更・影響調査）※独立した調査は並列
  ↓
調査結果を提示 → ユーザーに続行/中止の確認
  ↓
修正箇所のリストアップ
  ↓
Gemfile のバージョン制約更新
  ↓
bundle update rails
  ↓
rails app:update 実行（コンフリクト対応）
  ↓
変更ループ: 1ファイルずつ修正 → [直列] test → [並列] 静的解析・コードレビュー
  ↓
最終確認: [並列] 静的解析 / [直列] 全テスト → システムテスト
            └ 実行中に [並列] レビュー / 機密情報スキャン / ドキュメント同期 / 翻訳の検出
  ↓
コミット → プッシュ → PR作成 → 報告
  ↓
Codexレビュー（定期確認・指摘対応） → マージ・後片付け
```

## フェーズ1: リサーチ

### 1.1 現在のバージョンとアップグレード先の決定

以下のファイルから現在のバージョンを確認する。

- `Gemfile` の `gem "rails", "~> X.Y.Z"`
- `Gemfile.lock` の `rails (X.Y.Z)`

アップグレード先のバージョンを決める。以下の方針で選択する。

- **マイナーバージョンアップ**（例: 8.1 → 8.2）: メジャーバージョン内の最新安定版。破壊的変更が少ない
- **メジャーバージョンアップ**（例: 8 → 9）: 大規模な変更が含まれる可能性が高い。マイグレーションガイドを必ず確認する

### 1.2 リリースノートの確認

Railsガイドのリリースノートを確認する。

- アップグレードガイド: `https://guides.rubyonrails.org/upgrading_ruby_on_rails.html`
- バージョン別リリースノート: `https://guides.rubyonrails.org/X_Y_release_notes.html`
- Rails公式ブログのリリース記事

以下の分類で変更をリストアップする。

- **🔴 破壊的変更**: 削除されたAPI、非推奨機能の削除、デフォルト動作の変更
- **🟡 影響中程度の変更**: 新たに非推奨になった機能、設定変更の推奨
- **🟢 新機能**: 追加された機能

### 1.3 使用gemとの整合性調査

全gemについて、新しいRailsバージョンで動作するか確認する。

- Gemfile.lock の全gemについて、`required_ruby_version` だけでなく Rails 本体への依存関係も確認する
- Rails engine として動作するgem（Devise, ActiveAdmin, Ransack 等）は特に注意する
- Solid Cache / Queue / Cable 等、Rails本体と密接に関連するgemの対応バージョンを確認する

#### 調査結果の記録

以下のテーブル形式で記録する。

| gem | ロックバージョン | Rails新バージョン対応 | 対応が必要な場合の新しいバージョン |
|-----|----------------|---------------------|--------------------------------|
| solid_cache | 1.0.10 | 未確認 | 確認中 |
| ... | ... | ... | ... |

### 1.4 非推奨警告の確認

現在のコードベースで、Railsの非推奨警告（deprecation warnings）が出力されていないか確認する。

```bash
bin/rails log:clear
# アプリケーションを起動していくつかの画面を開くか、テストを実行
bin/rails test 2>&1 | grep -i "deprecat"
```

### 1.5 アプリケーションコードの影響調査

以下の観点でアプリケーションコードを調査する。

- 非推奨メソッド・古いAPIの使用
- 新しいデフォルト設定との互換性
- 削除されるライブラリへの依存
- データベースアダプタ（SQLite / PostgreSQL）の互換性

```

## 🔴 破壊的変更（対応が必要なもの）
- ...

## 🟡 影響中程度の変更
- ...

## 🟢 新機能（利用できそうなものがあれば）
- ...

## Gem 整合性
- ブロックするgem: なし / （あればリストと対応方法）

## アプリコードへの影響
- ...

## 修正が必要なファイル
- ...

## 判断
このままバージョンアップを続けますか？
```

ユーザーの回答を待つ。

- ユーザーが「続ける」と答えた → フェーズ3へ進む
- ユーザーが「中止」と答えた → ここで終了

## フェーズ3: 修正箇所のリストアップ

影響調査結果を基に、修正が必要なファイルを全てリストアップする。

| ファイル | 修正内容 | 影響度 |
|---------|---------|--------|
| `Gemfile` | `gem "rails", "~> X.Y.Z"` の書き換え | 必須 |
| `Gemfile` | 関連gemのバージョン制約更新 | 状況による |

| `docs/*.md` | ドキュメント内の古いRailsバージョン表記を更新（`rg` で旧バージョンを検索して確認） | 必須 |
| アプリケーションコード | 削除/非推奨APIの置き換え | 状況による |

## フェーズ4: Gemfileの更新

### 4.1 バージョン制約の書き換え

```ruby
# Gemfile
gem "rails", "~> X.Y.Z"
```

### 4.2 関連gemのバージョン確認

Railsと密接に関連するgem（solid_cache, solid_queue, solid_cable 等）のバージョン制約も必要に応じて緩和する（または新しい制約を確認する）。

### 4.3 bundle update

```bash
bundle update rails
```

依存関係の競合が発生した場合:

1. 競合しているgemを特定する
2. そのgemの新しいバージョンが公開されているか確認する
3. 新しいバージョンに更新するか、代替gemを検討する
4. 解決できない場合はユーザーに報告し判断を仰ぐ

## フェーズ5: rails app:update の実行

```bash
bin/rails app:update
```

このコマンドは新しいRailsバージョンのデフォルト設定ファイルを生成する。コンフリクトが発生した場合は以下の手順で対応する。

### 5.1 ファイルごとの差分確認

`rails app:update` が示す各ファイルの差分を確認する。

- `config/application.rb`
- `config/environments/development.rb`
- `config/environments/production.rb`
- `config/environments/test.rb`
- `config/initializers/` 以下のファイル
- `config/database.yml`
- `bin/` 以下のファイル
- `config/boot.rb`
- その他

### 5.2 コンフリクト解決方針

- **新しいデフォルト設定**: 新しいデフォルト設定を採用することを基本とする。ただし、アプリケーションの動作に影響する重大な変更（認証・セッション・CORS等）は、ユーザーに確認してから変更すること
- **削除された設定**: 古いバージョンの設定が削除された場合、新しい方法に移行する
- **削除・非推奨になった設定**: 対象バージョンのアップグレードガイドを確認し、古い設定を単に抑制せず新しい方法へ移行する

`config/` 以下の変更はアプリケーション全体の動作に影響するため、1ファイルずつ慎重に確認し、必要に応じてユーザーに確認を取ること。

## フェーズ6: 変更ループ

**重要**: 修正箇所が多い場合でも、いっぺんに全てのファイルを修正してはならない。1ファイルまたは1論理グループずつ、以下のループを回すこと。

### ループ1周の手順

1. **修正**: 1つのファイル（または密接に関連するファイル群）を修正する
2. **ユニットテスト実行**: `bin/rails test` でテストがパスすることを確認する（テスト同士は直列。全テスト・システムテストは並列にしない）
3. **静的解析・セキュリティ（並列）**: Gem変更後の `bin/tapioca gem`、Rails DSL由来の型情報変更後の `bin/tapioca dsl` は先に実行し、その後 `bundle exec srb tc`・`bin/rubocop`・`bin/brakeman --no-pager`・`bin/bundler-audit` を**同一メッセージで並列実行**して、指摘があれば修正する
4. **コードレビュー**: 別エージェント（task ツール使用）によるレビューを依頼する。レビューは読み取り専用のため手順3と同一メッセージで並列起動してよい（並列実行ポリシー参照）
5. **問題があれば修正してループ**: 上記のいずれかで問題が見つかった場合は修正して再度ループする
6. **問題なければ次の修正へ**: 次のファイル/グループの修正に進む
7. **ユーザー向け文言の変更**: ビュー・flash・バリデーション・メール等の文言を追加・変更した場合は `.agents/skills/translation/SKILL.md` に従い翻訳の抜けを確認する

このループを、フェーズ3でリストアップした全ての修正が完了するまで繰り返す。

### 実行順序の推奨

1. `Gemfile` の変更 → `bundle update rails`
2. `rails app:update` で生成された新しい設定ファイルの適用
3. 初期化ファイル（`config/initializers/`）の修正
4. アプリケーションコードの修正（非推奨APIの置き換え等）
5. テストコードの修正
6. `Dockerfile` 等のインフラ関連ファイルの修正
7. **ドキュメントのバージョン表記更新**: `README.md`, `AGENTS.md`, `docs/*.md`

## フェーズ7: 最終確認

全修正が完了したら、以下のコマンドを全て実行し、すべてがパスすることを確認する。

静的解析（`bundle exec srb tc`・`bin/rubocop`・`bin/brakeman --no-pager`・`bin/bundler-audit`・`bin/importmap audit`）は相互に独立しているため、**同一メッセージで複数の bash ツール呼び出しを行って並列実行**してよい。全テストとシステムテストはテストDB・ブラウザ資源を共有するため直列化する。待ち時間が長いシステムテストの実行中は、コードレビュー・セキュリティレビュー・機密情報スキャン・ドキュメント同期・翻訳の検出を**同一メッセージで並列起動**してよい（翻訳の編集は完了後。並列実行ポリシー参照）。

```bash
# 最終確認の終了ステータス（既定は成功の0。失敗があれば1にする）
status=0

# 全テスト
bin/rails test || status=1

# システムテスト（必要な場合）
bin/rails test:system || status=1

# 型チェック
bundle exec srb tc || status=1

# Rubocop
bin/rubocop || status=1

# セキュリティスキャン
bin/brakeman --no-pager || status=1
bin/bundler-audit || status=1
bin/importmap audit || status=1

# Railsバージョン確認
bin/rails about || status=1

# ドキュメント内の古いバージョン表記が残っていないか確認（rg: 一致あり=0 / 一致なし=1 / エラー=2）
# 一致があれば失敗扱いとし、エラー終了も失敗とする（一致なしの1だけが成功）
rg -n '旧バージョン（ドット省略なしの完全なバージョン番号）' README.md AGENTS.md docs/ 2>/dev/null
rg_status=$?
if [ "$rg_status" -ne 1 ]; then status=1; fi

exit "$status"
```

ユーザー向け文言を変更した場合は `.agents/skills/translation/SKILL.md` に従い、全localeで未翻訳キー・直書き文言が残っていないことを確認する。

## フェーズ8: デグレーションチェック

テストだけでなく、実際にアプリケーションを起動して以下の観点で動作確認する。待ち時間が長いため、その実行中に読み取り専用のレビュー・監査、機密情報スキャン、ドキュメント同期、翻訳の検出を同一メッセージで並列起動してよい（並列実行ポリシー参照）。

```bash
# 開発サーバー起動確認
bin/rails server -p 3001 &
sleep 5
curl -s -o /dev/null -w "%{http_code}" http://localhost:3001/up
kill %1
```

確認項目:
- アプリケーションがエラーなく起動すること
- トップページが表示されること
- 管理画面にログインできること
- 投稿の一覧・詳細・作成・編集ができること
- Markdownレンダリングが正しく動作すること

## フェーズ9: セキュリティチェック

`git commit` を実行する前に必ず `.agents/skills/security-check/SKILL.md` の手順に従い、コミット対象の変更ファイルを対象とした機密情報スキャンを実行すること。リポジトリ全体のスキャンはユーザーが明示的に指定した場合のみ実行すること。

- 🔴 CRITICAL または 🟠 HIGH の指摘が見つかった場合はコミットを中断し、ユーザーに報告して指示を仰ぐこと
- 🟡 MEDIUM 以下の指摘のみの場合は報告を行うが、ユーザーの判断でコミットを継続してよい

## フェーズ10: コミット・報告

```bash
git add <該当ファイル>
git commit -m "{日本語のコミットメッセージ}"
```

コミット後、以下の内容をユーザーに報告する。**報告は日本語で行う**（中国語など他言語を混入させない）:

- アップグレード元・先のバージョン
- 変更したファイルのリスト
- テスト・静的解析の結果（すべてパスしたこと）
- デプロイ時の注意点（新しい設定、非推奨警告、DBマイグレーションの要否等）
- 可能であれば、軽く動作確認（`bin/rails s` で起動確認等）をしておくこと

コミット後は `git push origin <ブランチ名>` でプッシュし、PRを作成する。「完了後のフロー」に従い、Codexレビューの定期確認・妥当な指摘への対応・指摘がなくなった後のmainへのマージ・後片付け・ノウハウ保存まで進める。マージ・後片付け後にも本番デプロイ手順（マージコミットの完全SHA）を提示する。マージ後の CI 確認は `.agents/skills/ci-verification/SKILL.md` に従う。
